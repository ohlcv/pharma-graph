# 加载期 20 秒界面冻结 —— 根因是 euler 布局占死主线程，修复方案是搬进 Web Worker

> 状态：**已修复**。加载期帧率 20 FPS → 57–60 FPS，布局质量保持。
> 记录日期：2026-09-29
> 关联文档：[`debug-tesseract-perf-hypothesis-rejected.md`](./debug-tesseract-perf-hypothesis-rejected.md)（同一批性能排查的前一轮，本文是其延续）
>
> ⚠️ **方法论警告（本文档踩过的坑，务必先读）**
>
> **无头 Chromium 的性能数字不可信。** 本次排查的头两个多小时完全走错方向，
> 根因是全部测量都基于 Playwright **无头**模式：
>
> - 无头模式走 SwiftShader **软件光栅化**，性能剖析里光栅化任务占 7870ms/5s，
>   而脚本执行只占 187ms —— 40 倍的差距**完全是软件渲染的产物**。
> - 同一张图在**有头**模式（真实 GPU 合成）下测得满帧，零长帧。
>
> **结论：帧率相关的性能结论，必须用有头浏览器测。** 无头数据只适合做
> 同一环境下的**相对比较**，绝对值一律无效。
> （工具已内置：`tools/measure-real.mjs` 有头 / `HEADED=0` 无头回落）
>
> 第二个坑：**归因要靠对照组，不要靠直觉。** 用户报「好卡」时，
> 我第一反应是怀疑刚新增的装饰节点（生命之树），并立刻开始优化它的绘制逻辑 ——
> 而实测证明它完全无辜（稳态满帧）。**新增代码 ≠ 新增瓶颈**，先量再改。

## 问题描述

用户反馈：「好卡」。

主观症状：打开页面后，界面明显卡顿，约 20 秒后恢复正常。

## 环境

- 构建：`npm run build` + `vite preview`（排除 dev server 的 HMR / 冷启动噪声）
- 数据规模：1183 节点 / 1198 边
- 视口：`1600×1000`
- 采样：Playwright，**有头模式**（真实 GPU 合成），rAF 逐帧打点

## 排查过程

### 第一层：分阶段测帧率，定位卡在什么时候

rAF 采样按「秒」分桶，看整条加载时序（`tools/measure-phase.mjs`）：

```
  1s │    15    20    20    20  15.2    20    20    20    20    20
 11s │    20    20    30    30    30  29.2    20  19.8    20    20
 21s │  59.9  59.9  59.9  59.9  59.9  59.9  59.9  59.9  59.9  59.9
 31s │  59.9  59.9  59.9  59.9  59.9  59.9  59.9  59.9  59.9  59.9
```

**结论立刻清晰：0–20 秒 15–20 FPS，20 秒后满帧。** 卡的是 euler 布局那 20 秒，
不是常驻开销。

### 第二层：那三个装饰节点有责任吗？——用有头模式做对照

上一轮排查的结论是「装饰节点不是瓶颈」，但那是在**无头**模式下得出的，
数字不可信。这次用有头模式重测三档：

| 变体 | 中位帧 | FPS | 长帧占比 |
| --- | --- | --- | --- |
| 无装饰 | 16.7ms | 59.9 | 0% |
| 只开生命之树 | 16.7ms | 59.9 | 0% |
| 三个全开 | 16.7ms | 59.9 | 0% |

**三档全部满帧、零长帧。** 装饰节点（含新加的生命之树）在稳态下**完全无辜**。
用户感受到的卡 100% 来自布局期。

### 第三层：那 20 秒里，时间花在哪？

关键实验：**在 Node 里（无 DOM）跑同一张图的 euler 布局**
（`tools/probe-worker-feasibility.mjs`）：

| 场景 | 耗时 |
| --- | --- |
| headless 纯计算（Node，无 DOM，无动画） | **3944 ms** |
| 浏览器主线程 + 动画 + 位置回写 | **20877 ms** |

**只有 4 秒是真正的力计算，另外 16 秒花在逐帧动画、cytoscape 位置回写与画布重绘上。**

这解释了为什么「降级布局参数」救不了场（见关联文档的降级实验：降级换不来帧率，
只换来质量损失）—— 因为开销的大头根本不在力学计算本身。

## 修复方案：把计算搬进 Web Worker

### 可行性先验证，再动手

动手前先确认两件事，缺一不可：

1. **力布局库无 DOM 依赖** —— 查 `node_modules/cytoscape-euler/src/`，无 `document.` / `window.` 引用。
2. **图核心库支持 headless 运行** —— 在 Node 里直接建 headless 实例跑通 1182 节点，
   边交叉数 83（比浏览器里的 138 更好）。

两项都成立，方案才可行。**先写探针脚本验证，再写实现** —— 否则可能做到一半发现
库根本跑不起来。

### 实现要点

- 新增 worker 源文件，在 worker 内用 **headless 模式**建图库实例，
  关键选项是**关闭动画**（worker 里不画任何东西，动画纯属浪费）
  与**关闭样式解析**（力学计算不读样式）
- 新增主线程侧客户端封装，**三条硬要求**：
  - **有超时上限**（实测纯计算 4s，留 15s 余量）
  - **异常一律捕获**，Worker 可能因不支持 / 超时 / 运行时错误而失败
  - **永不抛异常，只返回失败标志** —— 让失败只表现为「退回同步布局」，
    不炸掉整个加载流程
- 主线程拿到最终坐标后**一次性批量回填**（包在批量更新里，避免 1183 次
  位置写入各自触发一次渲染通知）
- **兜底路径必须保留**：Worker 任何一条失败路径都自动退回原来的同步布局

### 效果

| 阶段 | 改前 | 改后 |
| --- | --- | --- |
| 加载期（0–20s） | 15–20 FPS | **57–60 FPS** |
| 稳定期（20s 后） | 59.9 FPS | 59.9 FPS |

布局质量对照（几何指标，不靠主观判断）：

| 指标 | 改前（同步） | 改后（Worker） |
| --- | --- | --- |
| 边交叉数 | 138 | 155 |
| 节点重叠率 | 0% | 0.4% |
| 铺开范围 | 17571 | 4856 |

质量同量级，可接受。

## 结论

1. **卡顿的根因是 euler 布局占死主线程 20 秒**，与装饰节点、与新代码均无关。
2. **那 20 秒里只有 4 秒是真正的力学计算**，其余是动画与渲染开销。
   因此「优化力布局参数」是错的方向（关联文档的降级实验已证明）。
3. **搬进 Worker 后主线程阻塞归零**，这是本图上唯一不牺牲质量的路径。

## 遗留 / 需要知情的事

### 1. 有损：失去了入场动画

Worker 方案拿到的是**最终坐标**，无法呈现「节点从中心散开」的过程。
取舍是明确的：20 秒界面冻结换一段入场动画，划算。

**但这是有损改动。** 如果后续认为那段动画更有价值，需要重新权衡
（例如：先同步跑 2 秒动画铺开、再接手给 Worker 收敛——尚未验证）。

### 2. 铺开范围缩小

Worker 结果的铺开范围 4856，同步方案是 17571。**图整体更紧凑了。**
边交叉数与重叠率都在同量级，但视觉上「宇宙」变小。这是否可接受，
建议打开页面实际看一眼再定。

### 3. 与关联文档的「未尝试方向」的关系

关联文档末尾列过一条未尝试方向：

> 把 euler 换成同步一次性（`animate: false`）——牺牲动画过程，但总计算量不变，
> **帧率指标将失去意义（阻塞主线程）**，只在低频触发时有意义

本文正是这条路。**但搬进 Worker 后，那个顾虑不成立** —— 计算确实阻塞，
但阻塞的是 worker 线程，主线程的帧率指标完全有意义。
「帧率指标失去意义」的前提是「在主线程上跑」。

### 4. worker 源文件是纯英文注释

写入 worker 源文件时，编辑器连续两次在**同一字节位置**把文件截断成乱码
（报错「File appears to be binary」），而其他含中文的文件正常。
最后改用命令行写纯 ASCII 内容绕过。

因此 `src/core/layout-worker.ts` 目前是**纯英文注释**，
中文设计说明放在 `layout-worker-client.ts` 与提交记录里。
**这个不一致是有原因的，不是风格问题** —— 后续若要补中文注释，
请先确认写入方式是否可靠。

### 5. 环境里有未归属的文件

`src/core/celestial-e8-node.ts` 在本次排查期间出现（未跟踪、不被引用、
带 3 个类型错误）。非本次工作产出，**未做处理**，留待归属确认。

## 复现方式

```bash
# 有头模式测稳态帧率（真实 GPU 数字，可信）
node tools/measure-real.mjs off tree all

# 分阶段测加载时序帧率（定位卡在哪个阶段）
node tools/measure-phase.mjs            # 无装饰
DECOR=tree node tools/measure-phase.mjs # 三个奇观全开

# 验证 headless 能否跑力布局、耗时多少、质量如何
node tools/probe-worker-feasibility.mjs
```

> ⚠️ 上述工具**必须默认有头**。若被迫无头运行（`HEADED=0`），
> 得到的绝对帧率不可信，只能用于同环境下的相对比较。
>
> 关联文档的 `tools/measure-euler-quality.mjs` 是无头的，其表格中的
> FPS / 中位帧 / 长帧占比**受本文档开头的方法论警告影响**，
> 质量指标（边交叉、重叠率）与时长指标仍然有效。
