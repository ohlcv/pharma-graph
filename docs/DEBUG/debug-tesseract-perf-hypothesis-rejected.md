# 四维空间（tesseract）装饰节点疑似拖慢加载与力布局帧率 —— 假设被否证

> 状态：**已排除**。装饰节点不是瓶颈，瓶颈是 1182 节点的 euler 力布局本身。
> 记录日期：2026-09-28

## 问题描述

加入「四维空间（tesseract）」装饰节点后，主观感觉：

1. **初始加载明显变慢**
2. **力布局（euler）运行期间帧数大幅降低**

怀疑该节点（真实 cytoscape 节点 + 独立全屏 canvas 逐帧重绘）在布局每帧都整幅重绘，把主线程占满。

## 环境

- 构建：`npm run build` + `vite preview`（**不用 dev server**，排除 HMR / 冷启动噪声）
- 数据规模：1182 节点
- 采样：Playwright，`1600×1000` 视口，页面加载后立即开始 rAF 打点，跑满 22s（覆盖 euler 全程）
- 指标：rAF 帧间隔分布（中位 / p90 / p99 / max）+ 长帧（>50ms）占比

## 排查过程

### 第一层：先确认「装饰节点开着时有多慢」

只测全开状态：

```
中位帧间隔 115.7ms (≈8.6 FPS)，p90 140.7ms，长帧占比 61.8%
```

结论：帧率确实很差 —— **但这只能说明「慢」，不能说明「是谁慢」**。1182 节点的 euler 本身就慢，这是没有对照组的裸数据。

### 第二层：单独关掉超立方体

在 `main.ts` 加开关，只关超立方体、保留太极八卦（两者机制完全相同，构成干净对照）：

| 指标 | 全开 | 只关超立方体 |
|---|---|---|
| 中位帧间隔 | 115.7ms | 128.2ms |
| 长帧占比 | 61.8% | 62.1% |
| 平均 FPS | 10.7 | 9.2 |

**关掉之后没有变快，反而略差。** 初步否证「超立方体是元凶」。

### 第三层：四组对照 + URL 开关

把两个装饰节点都做成 URL 可控（`?decor=off|celestial|tess`，缺省全开），在一台 server 上跑完所有组，避免反复构建带来的噪声：

| 组合 | 太极 | 超立方体 | 中位ms | FPS | 长帧% |
|---|---|---|---|---|---|
| `decor=off` | 关 | 关 | 116.4 | 8.6 | 79.9% |
| `decor=celestial` | 开 | 关 | **104.7** | **9.6** | 81.3% |
| `decor=tess` | 关 | 开 | 110.2 | 9.1 | 81.8% |
| 缺省（全开） | 开 | 开 | 120.2 | 8.3 | 80.4% |

## 结论

1. **四组差异全部落在测量噪声内**，长帧占比都死在 80% 上下。装饰节点对布局帧率**没有可观测影响**。
2. **全关（`off`）不是最快的一组**，最快的反而是只留太极八卦 —— 说明两套装饰之间也不存在互相挤占。
3. **「加载变慢」也没被证实**：`domReady` 在四组间是 1191ms / 2006ms / 4187ms / 13038ms，跨度 10 倍，但这个顺序与装饰节点数量**不相关**（只留一个的那两组反而一个最快一个最慢）。这是 preview server 冷启动 + 浏览器缓存状态的噪声，不是真实负载差异。
4. **真正的瓶颈是 euler 布局本身**在 1182 节点规模下的固有代价，装饰节点只是恰好和它一起被引入，时间上相关但非因果。

## 处理

- **不删除** `createTesseractOverlay()` 调用。保留 `?decor=` URL 开关（`src/ui/main.ts` 的 `DECOR_OVERRIDE`）作为后续对照实验工具，默认仍是两个都开。
- 早期版本曾在注释里写「实测它把帧率拖到 8.6 FPS」—— 那是**把裸数据当成了因果结论**，已更正为四组对照数据。

## 遗留 / 下一步

如果确实要提升布局期帧率，该优化的是 euler 本身，而不是装饰节点：

- `layoutstop` 之前是否可以降级布局质量（`quality` / `refresh` / 关闭 `nest` 嵌套预布局）
- 1182 节点是否值得引入**分层/分块布局**（先对子图布局，再整体展开）
- 装饰节点的 canvas 是否可以在布局期间降频（`位置跟随 throttled rAF`）—— 鉴于本文件结论，即便做了预期收益也接近 0，**优先级低**
- 加载期是否该先渲染静态骨架、待布局稳定再挂装饰层
