# 节点构建规则

> 适用范围：药学知识图谱的节点创建、编辑与结构维护。
>
> 配套文档：[frontmatter.md](./frontmatter.md) — frontmatter 字段定义与视觉编码规范（权威来源）。
>
> 原则：忠实保留药学语义，不丢边、不丢正文。

***

## 〇、设计理念

本项目采用 OWL/RDF 风格的 **5 种边关系类型** + **10 种节点本质** 的本体建模：

- **节点本质**：module / strict-class（五边形） / umbrella-class（六边形） / medication（重点药） / drug（普通药） / illness / mnemonic / summary / notion / concept（正方形）
- **边关系**：`subclass_of` / `part_of` / `instance_of` / `disjoint_with` / `equivalent_to`

> **`medication` vs `drug`**：均为椭圆。`medication` = 教材中**详细讲解的药物**（有完整药理卡片），柔橙填充；`drug` = 教材中**仅提名的药物**（只点名、未详讲），柔蓝填充。区分依据是教材里这张药**是不是被"画像"过**。

详细语义见下文「edges_out.type — 边类型」章节。

## 零、命名规范

### 命名格式

**统一格式：`前缀-节点英文名-后缀（章节位置）`**

- **前缀**：表示节点本质，一眼判断类型
- **节点英文名**：药物或分类的英文/拉丁文名称
- **后缀**：章节位置，格式为 `{书简写}-{章号}-{节号}`（如 `y2-02-01`）

### 章节位置后缀

| 书 | 书简写 | 章号 | 节号 | 示例后缀 |
| --- | ------ | ---- | ---- | ------- |
| 药学专业知识一 | `y1` | 两位数字 | 两位数字 | `y1-01-01` |
| 药学专业知识二 | `y2` | 两位数字 | 两位数字 | `y2-02-01` |
| 药学综合知识与技能 | `y3` | 两位数字 | 两位数字 | `y3-04-05` |
| 药事管理与法规 | `y4` | 两位数字 | 两位数字 | `y4-01-01` |

| essence | 中文含义 | 形状 | 使用范围 |

| `umbrella-class` | 伞形分类（粗分类） | 六边形 | 按临床用途、功能、机制、酶划分的聚类集合 |
| `concept` | 概念/术语 | 正方形 | 教材定义明确、具有边界的知识概念 |
| `medication` | 重点药（详细讲解） | 椭圆 | 教材中有完整药理卡片的药物：药理作用、机制、用法、不良反应等 |
| `drug` | 普通药（仅提名） | 椭圆 | 教材中只点名提及、未详细讲解的药物 |
| `illness` | 疾病/病理状态/综合征 | 菱形 | 可被治疗、禁忌、导致或独立讨论的疾病/状态 |
| `notion` | 学习性认知单元 | tag | 经验性认识、临床提示、易混概念、经验归纳 |
| `mnemonic` | 记忆口诀 | vee | 口诀、首字母记忆、顺口溜、分类速记 |
| `summary` | 总结/归纳 | 八边形 | 对多个节点进行收束、压缩、归纳的总结节点 |

### edges_out.type — 边类型（决定边的颜色、虚实与方向）

**只使用以下 5 种边类型**，不得自创其他 type：

| type | 中文 | 核心语义 | 方向规则 | 线型 | 颜色 |
| ---- | ---- | -------- | -------- | ---- | ---- |
| `subclass_of` | 是一种（类-类） | A 是 B 的一种子类，集合 A ⊂ 集合 B | **子类 → 父类** | 实线+三角箭头 | 蓝色 |
| `part_of` | 是一部分（局部-整体） | A 是 B 的一个构件、片段、模块，A 不是 B 的一种 | **局部 → 整体** | 实线+三角箭头 | 绿色 |
| `instance_of` | 是实例（个体-类） | A 是 B 的一个实例/代表药物 | **实例 → 类别** | 实线+三角箭头 | 橙色 |
| `disjoint_with` | 互斥 | 两类互斥，不能同时属于 | **对称（A ↔ B，存一条即可）** | 点划线 | 紫色 |
| `equivalent_to` | 等价 | 两名称语义完全相等 | **对称（A ↔ B，存一条即可）** | 点线 | 灰紫 |

### 边关系语义详解

#### subclass_of — 类-类，A 是一种 B

> A `subclass_of` B → A 是 B 这个大类里的小种类，**二者都是类**。
>
> 集合视角：A 集合 ⊂ B 集合。

**方向**：子类 → 父类

**示例**：
```yaml
# 短效苯二氮䓬 subclass_of 苯二氮䓬类
# 西药一 subclass_of 执业药师（西药）考试科目
edges_out:
  - target: 苯二氮䓬类
    type: subclass_of
    reason: 一种苯二氮䓬
```

#### part_of — 局部-整体，A 是 B 的构件

> A `part_of` B → A 是 B 内部的一个构件、片段、模块，**A 不是 B 的种类**。

**方向**：局部 → 整体

**示例**：
```yaml
# 不良反应 part_of 药物画像
# 口诀 part_of 知识体系
# 第一节 part_of 第一章
edges_out:
  - target: 药物画像
    type: part_of
    reason: 是药物画像的一部分
```

#### instance_of — 个体-类，A 是 B 的实例

> A `instance_of` B → A 是 B 的一个具体实例（通常是具体药物 → 伞形/严格分类）。

**方向**：实例 → 类别

**示例**：
```yaml
# 丁苯酞 instance_of 改善脑功能药
# 地西泮 instance_of 苯二氮䓬类
edges_out:
  - target: 改善脑功能药
    type: instance_of
    reason: 是一种改善脑功能药物
```

#### disjoint_with — 互斥（对称）

> A `disjoint_with` B → A 和 B 互斥，不能同时成立。

**方向**：对称（A ↔ B，存一条即可）

**示例**：
```yaml
# 苯二氮䓬类 disjoint_with 非苯二氮䓬类
edges_out:
  - target: 非苯二氮䓬类
    type: disjoint_with
    reason: 互斥分类
```

#### equivalent_to — 等价（对称）

> A `equivalent_to` B → A 和 B 语义完全相等（等价名、同义词）。

**方向**：对称（A ↔ B，存一条即可）

**示例**：
```yaml
# 阿司匹林 equivalent_to 乙酰水杨酸
edges_out:
  - target: 乙酰水杨酸
    type: equivalent_to
    reason: 等价名
```

## 四、depth — BFS 自动推导（决定边框色）

`depth` 是自动推导的思维导图深度，**不需要 frontmatter 字段**，由 build-graph 在图构建阶段通过 BFS 从根节点计算：

| depth | 含义 | 典型节点 |
| ----: | ---- | -------- |
| `0` | 中心节点（根入口） | 执业药师考试体系、药学专业知识一/二 |
| `1` | 第一层子节点 | 篇入口、章入口 |
| `2` | 第二层 | 节入口、伞形分类 |
| `3` | 第三层 | 严格分类、具体药物/疾病 |
| `4` | 第四层 | 口诀、总结、辅助认知节点 |

> **父子判定规则**：`depth` 数字大的节点是子节点（距离根更远）。分类层级用 `subclass_of`；章节局部→整体用 `part_of`。

**BFS 推导逻辑**（build-graph.ts）：
1. 找 `in_degree == 0` 的节点作为根节点，`depth = 0`
2. 沿 `edges_out` 往外 BFS，每跳一步 `depth + 1`
3. 每个节点只被访问一次，取最早到达的路径深度
4. 未被任何边连接的孤立节点 `depth = 0`

## 五、合并规则

### 5.1 核心原则

1. **语义不丢**：合并节点的正文必须全部内化进目标节点。
2. **边不丢**：合并前先确认入边；若 > 0，需先确认边归属再删除。
3. **不重建已删节点**：合并提交只改源节点正文 + 删除源 md，不新增节点。
4. **schema 与内容分离**：字段规范与正文内容各自独立提交。

### 5.2 合并候选识别（4 条信号）

| 信号                                                 | 含义         | 处置                     |
| -------------------------------------------------- | ---------- | ---------------------- |
| ① `in_deg == 0` 且 essence 非 `medication`/`illness` | 零散节点       | 优先就地扩伞形/节正文；无合并去向则直接删除 |
| ② 伞形 module 正文缺机制/口诀段，但同级伞形都有                      | 结构不对称      | 把 in\_deg=0 的零散节点内化进伞形 |
| ③ 伞形 module 正文已包含与同目录 concept 完全重复的内容              | 已合并但忘了删 md | 直接删除 concept           |
| ④ 节节点正文已包含与同目录 concept 完全重复的内容                     | 同上         | 同上                     |

**不视为合并候选**：

- `in_deg == 0` 但 essence 是 `medication` 或 `illness`（具体药物/疾病是图谱一等公民）

- `in_deg > 0`（有入边即被引用，需先确认边归属再合并）

### 5.3 合并去向决策

1. **伞形 module 正文的对应段** — 零散 concept 的内容天然属于伞形语义。
2. **节节点正文的相关段** — 跨伞形总论性 concept 归节。
3. **直接删除** — 当节点纯粹是孤立冗余，无任何合并价值时。

### 5.4 新版变化：口诀/注意不再强制合并

口诀/注意独立成节点的规则如下：

- 口诀（`mnemonic`）、总结（`summary`）**可以独立成节点**。

- 判断标准：纸质思维导图上有独立框/独立分支的 → 独立；只是考点旁标注文字的 → 内嵌。

- 独立的口诀/注意节点**自身**用 `part_of` 边指向主知识节点（不是反过来）。详见 §5.15。

### 5.5 骨架边补齐（与合并正交）

当某章节的伞形 module `in_deg=0`，但本来应该有层级边指向父级时，属骨架缺失而非过度拆分。

| 场景                      | 处置           |
| ----------------------- | ------------ |
| 节点零入度 + 有自身语义           | 合并到伞形/节正文    |
| 节点零入度 + 是骨架本身（伞形/药物/疾病） | 补 `subclass_of` / `part_of` 边 |
| 节点零入度 + 是图入口（节、章、book）  | 不动           |

### 5.6 禁止冗余空模块

**不得创建纯视觉分区的空 wrapper 节点。** 每个节点必须有独立知识语义。

| 场景                           | 处置               |
| ---------------------------- | ---------------- |
| 创建"分类与代表药品"空模块（只做视觉分区，无独立语义） | ❌ 删除，药物直接挂到分类节点  |
| 创建"临床用药评价"空模块（只做视觉分区，无独立语义）  | ❌ 删除，临床评价下沉到药物节点 |
| 章级入口（有完整 summary + 语义）       | ✅ 保留             |
| 节级入口（有完整 summary + 语义）       | ✅ 保留             |

### 5.7 临床内容下沉模式

药物节点的临床内容（药理作用、适应症、禁忌、相互作用）**写入** **`summary.full`** **字段**，不拆成独立的 `instance_of` / `part_of` 边。

```yaml
# ✅ 正确：临床内容在 summary.full
summary:
  short: 吡拉西坦是酰胺类代表药，改善脑代谢。
  full: >-
    【药理作用】作用于大脑皮质，激活神经细胞…
    【适应症】急慢性脑血管病所致记忆减退…
    【禁忌】锥体外系疾病、亨廷顿舞蹈症禁用…
    【相互作用】与华法林合用延长凝血酶原时间…

# ❌ 错误：为每个临床关系建独立边
edges_out:
  - target: some-disease
    type: instance_of
    reason: 治疗
  - target: some-adr
    type: instance_of
    reason: 导致
```

**何时用 `instance_of` 边、何时用 summary.full？**

| 场景                     | 做法                |
| ---------------------- | ----------------- |
| 药物→疾病的对应关系需要图谱导航       | `instance_of` 边 + 独立疾病节点 |
| 药物的药理/适应症/禁忌/相互作用是知识文本 | `summary.full` 内嵌 |
| 药物之间的相互作用需要可视化         | `instance_of` 边          |
| 单纯的文字描述考点              | `summary.full` 内嵌 |

### 5.8 summary 字段填写原则

**`summary.full` 必须由用户手动提供，禁止 AI 自动填充。**

这是创建/重构节点文档时最容易越权的点，必须严格区分两类字段：

| 字段                | 创建时可自动初始化？   | 何时可填充/替换                                          |
| ----------------- | ------------- | ------------------------------------------------- |
| `summary.short`   | ✅ 可以（建议留空或简短占位） | 用户主动提供或确认后 **替换**（包括保留原值、手写改写、按用户指令重写）         |
| `summary.full`    | ❌ 禁止          | **仅当用户主动提供文本时** 才可写入；任何"智能补充"、"自动总结"、"按药理推断"都被禁止 |

**反模式（绝对禁止）**：

1. ❌ 创建新节点时由 AI 撰写 `full:` 内容，即使看起来"药理学上是正确的"。
2. ❌ 用通用占位字符串填充 `full:`（如 `"待补充"`、`"暂无内容"`），用户未要求时不得加占位。
3. ❌ 在用户改 `short` 时顺手重写 `full`，除非用户明确指示。
4. ❌ 把 `full` 拆成独立 `link` 边的同时，还往 `full` 字段里塞文字。两选一（见 §5.7）。
5. ❌ 用其它同章节、同分类节点的 `full` 文本进行"模板套用"——除非用户明确要求参照。

**正模式**：

1. ✅ 创建新节点时：若用户未提供 `full`，**该字段完全不写**（让 YAML 解析为 `undefined`，UI 自然隐藏"展开详情"按钮）。
2. ✅ 用户手写或口述一段内容并明确说"写入 full"：原样写入，不二次润色。
3. ✅ 用户明确要求"参考 X 节点的格式改写本节点的 full"：可以改写；否则不参照。
4. ✅ 用户只提供 `short`：仅替换/写入 `short`，**`full` 字段保持原样或不写入**，不留占位文本。
5. ✅ 用户提供多个药理点（如"作用：…用途：…禁忌：…"）：按用户给的标题分段写入 `full`，段落间用空行分隔（marked 会拆出多个 `<p>`）。

**汇报约定**：

- 创建/重构一个节点时，在最终汇报里**明示** `short`/`full` 两个字段分别做了什么（哪个是用户提供的、哪个是沿用旧的、哪个未改动、哪个为不写入）。
- 若用户未提供 `full`，汇报里必须出现 "未写 full / full 留空 / 待用户提供" 字样，便于用户知道该字段需要后续补充。

**判断锚点（self-check）**：

> "如果我不在场，用户能否接受我写进 `full` 的每一个字？"  
> 不能 → 删掉或留空；能 → 写。  
> 默认答案：**不能**，所以默认不写。

### 5.9 分类节点（classification）的内容归属

分类节点（`essence: classification`，如"酰胺类""乙酰胆碱酯酶抑制剂"）只承担**分类框架**作用：

| 内容类型                                     | 归属                                          |
| ---------------------------------------- | ------------------------------------------- |
| 分类的定义、范围、与其他分类的区别                     | 分类节点**自身**的 `summary.full`（用户手写补充时写入）     |
| 分类下每个具体药物的药理/适应症/禁忌/相互作用              | ❌ **不允许**写入分类节点；必须为**每个具体药物单独建立 `medication` 节点** |
| 该分类共用的学习要点（如"酰胺类共性：促进 Ach 合成"）          | 分类节点的 `summary.full`（用户手写补充时写入）              |

**反模式（绝对禁止）**：

1. ❌ 把"吡拉西坦的药理作用"写进"酰胺类"分类节点的 `summary.full` 里。药物内容必须下沉到药物节点。
2. ❌ 把多个药物的临床内容合并成一坨写进分类节点，再省略药物节点的 `summary.full`。
3. ❌ 把分类节点的 `summary.full` 当成"分类+所有药物摘要"的混合体。

**正模式**：

1. ✅ 分类节点只写分类自身的语义（"是什么""为什么这么分""共有特点"），正文简短。
2. ✅ 每个药物独立建 `medication` 节点，药物节点自己承载完整 `summary.full`。
3. ✅ 用户手写补充"该分类还需要一段总结性描述" → 写入分类节点 `summary.full`，作为分类的"上位总结"。
4. ✅ 用户未提供分类的总结性内容 → 分类节点 `summary` 可只写 `short`（或干脆不写）。

### 5.10 思维导图照片 → 节点字段的转录规则

用户提供思维导图照片（含荧光笔划线和手写补充）作为输入时，按以下规则把照片里的内容映射到节点字段：

| 照片里的内容                              | 写入哪                       |
| ----------------------------------- | ------------------------- |
| 图中**本来就有**的具体药物节点的正文内容（如药物名、药理描述） | 该药物节点的 `summary.full`     |
| 荧光笔划住的关键词 / 短语                      | **重组**为该药物节点的 `summary.short`（关键词用 `**…**` 加粗） |
| 用户**手写补充**的文字（不在原图里）               | 写入对应节点的 `summary.short`（手写补充是判断考点 / 重点的依据） |

**判定顺序（优先级从高到低）**：

1. **手写补充 > 图中原有**：用户手写的一定是新信息（强调 / 补充 / 订正），优先按手写内容写。
2. **荧光笔划住 > 普通印刷**：荧光笔划住的内容是该药物的核心考点，**重组成 short**，而非照搬原句。
3. **图中普通印刷**（非荧光笔）→ 该药物节点的 `full` 素材来源；非核心描述可酌情忽略（用户未要求全文录入时不录入）。
4. **同药物在多张照片出现** → 以"最新一张"为准；之前照片的差异向用户确认是否并入。

**正模式**：

1. ✅ 处理照片前，先用一句话告诉用户"我看到图里有 N 个药物节点、3 段手写补充，下面按 §5.10 转录"。
2. ✅ 转录 short 时，把"吡拉西坦是酰胺类中枢兴奋药"重新组织成"酰胺类中枢兴奋药，促进脑内**Ach↑**，激活、保护神经细胞"——关键词加粗。
3. ✅ 转录 full 时，**保留原图的【药理作用】【适应症】【禁忌】等段落标签**，按 §5.11 格式规范写。
4. ✅ 同一张照片里多个药物时，一次性处理完后**逐个汇报**哪个字段是手写、哪个是高亮重组、哪个是原文。

**反模式**：

1. ❌ 把荧光笔划住的字直接复制粘贴进 short，没有重组（用户高亮"组胺类、改善微循环血供"是为了强调，不是要原句）。
2. ❌ 把图中所有文字无差别全部复制到 full，忽略哪些是核心 / 哪些是噪音。
3. ❌ 在没有照片提供的节点上"按图谱惯例"自动推断 short——这是 §5.8 禁止的自动填充。

### 5.11 格式规范（short / full / tags / markdown 加粗）

#### 5.11.1 `summary.short` 格式

- 结构：**核心特点 + 核心用途**（或"作用 + 适应症"），用一句话说清"是什么 / 治什么"。
- 关键词：用 `**…**` 加粗（参见 §5.11.3 的关键词判定）。
- 句末：**不加句号以外的符号**（不用"。"以外的标点）。
- 不重复 `full` 已有的【适应症】段标签，避免 short 和 full 内容雷同。

✅ 例子（参见丁苯酞、倍他司汀等已落地节点）：

```yaml
short: 重构微循环、恢复能量代谢，芹菜过敏者禁用，用于轻中度**缺血性脑卒中**。
short: 组胺类药物，改善微循环血供，用于脑血管疾病和**内耳眩晕症**。
```

#### 5.11.2 `summary.full` 格式

- 多段结构，**前面必须标注清楚**章节标签，常用标签（不限于此，按实际内容选用）：
  - 【药理作用】【作用机制】
  - 【适应症】【用途】【临床应用】
  - 【禁忌】【禁用】【禁用人群】
  - 【不良反应】【副作用】【ADR】
  - 【相互作用】【配伍】
  - 【用法】【用法用量】【给药方案】
  - 【注意】【注意事项】【特殊人群】
  - 【药物过量】【解救】
- **段落之间必须空行**（YAML 块字符串内的空行）—— 否则 marked 不会拆出多个 `<p>`，所有内容会挤在一起（参见 `src/ui/markdown.ts` 中 `breaks: false` 的设定）。
- 每段开头**先写标签**，再写正文，例如 `【适应症】主要用于轻、中度急性缺血性脑卒中。`
- 标签内可以包含关键词的 `**加粗**`，但**不要在标签符号上做文章**（保留 `【…】` 的中文方括号样式）。
- 完整示例：

```yaml
full: |
  【药理作用】我国开发的新药，可重构缺血区微循环，恢复缺血区脑组织能量代谢，**抗脑血栓形成**和**抗血小板聚集**。

  【适应症】主要用于轻、中度**急性缺血性脑卒中**。

  【禁忌】对芹菜过敏者禁用（芹菜中所含的左旋芹菜甲素与本药化学结构相同）、有严重出血倾向者禁用。
```

#### 5.11.3 关键词判定与 `**加粗**`

加粗关键词的判断标准（满足任一条即可加粗）：

| 加粗条件                       | 例子                          |
| -------------------------- | --------------------------- |
| 药理学机制名词                    | **Ach↑**、**α受体拮抗**、**H₁受体** |
| 适应症（疾病名）                   | **急性缺血性脑卒中**、**内耳眩晕症**        |
| 禁忌关键人群 / 关键药名              | **芹菜过敏者**、**β受体拮抗剂**         |
| 用户**手写补充**时重点强调的词          | 用户笔记里的 `**…**` 直接保留        |
| 荧光笔划住的关键词                  | 照搬图中的高亮位置                   |
| 不良反应 / 严重警告                | 严重出血倾向、过敏等                  |

**不加粗的反例**：

- ❌ 把整段一句话加粗（失去重点）。
- ❌ 加粗"用于""是""的""和"等连接词。
- ❌ 同一句话里加粗超过 4 个词组（说明用户没提供足够信息，或 short 写得太长）。

#### 5.11.4 `tags` 字段

- **来源**：从 `summary.short` 和 `summary.full` 的内容里**抽取关键词**，不杜撰。
- 写法：首字母不大写，使用中文逗号分隔。

##### 5.11.4.1 三铁律

1. **复用优先**：如果 `summary` 里已经有合适的关键词，**直接复用**，**不要自作主张另造同/近义词**（与 frontmatter §四一致）。
2. **去重优先**：不写语义重复的标签——同一节点下不允许 `口诀` 与 `记忆口诀`、`禁忌` 与 `禁用`、`适应症` 与 `适用症` 等同/近义词并存。先出现则保留先出现的。
3. **不杜撰**：严禁把 `summary` 里没出现的概念放进 tags（否则图谱搜索时会出现"空标签命中"）。

##### 5.11.4.2 药物节点专属规则：分类 + 作用

> 药物节点（`essence: medication`）的 tags **必须同时包含**其所属分类和主要药理作用。

| 必须包含 | 示例 |
| --- | --- |
| **至少一个分类 tag** | `H1受体激动剂`、`他汀类`、`β受体阻滞剂` |
| **至少一个作用 tag** | `扩张血管`、`降压`、`改善微循环`、`抗炎` |

- 分类可以不止一个（如 `H1受体激动剂` + `抗胆碱能药`）。
- 分类和作用均优先从 `summary` 的 `**加粗**` 词中抽取。

```yaml
# 正模式
tags:
  - H1受体激动剂       # 分类（来自 summary 加粗）
  - 内耳眩晕           # 作用 / 适应（来自 summary 加粗）
  - 扩张毛细血管        # 作用（来自 summary.full 加粗）
  - 微循环改善         # 作用（来自 summary 上下文）
```

##### 5.11.4.3 抽取流程（AI 执行顺序）

1. **扫 `summary`**：抽出所有 `**加粗**` 短语 / 专有名词 / 药理分类词。
2. **按 §5.11.4.1 三铁律 + §5.11.4.2 药物规则** 过滤候选词。
3. **语义去重**：同/近义词只保留先出现的。
4. **硬约束再过滤**：不重复 essence/depth、不写本质词、不写整句。
5. **兜底自取**（仅当前 4 步拿不到目标数量时）：基于 `summary` 上下文自取，必须向用户汇报"自取了哪些"。

##### 5.11.4.4 正 / 反模式

**正模式**（来自 `倍他司汀.md`）：

```yaml
tags:
  - H1受体激动剂       # 分类 ← summary.full 加粗
  - 内耳眩晕           # 作用 / 适应 ← summary 加粗
  - 扩张毛细血管        # 作用 ← summary.full 加粗
  - 微循环改善         # 作用 ← summary 上下文
```

**反模式**：

```yaml
tags:
  - H1受体激动剂        # ✅ 来自 summary 加粗
  - 组胺类药物          # ❌ 与"H1受体激动剂"近义，保留先出现的，丢弃这条
  - 内耳眩晕症          # ✅ 来自 summary 的"内耳眩晕症"
  - 眩晕耳鸣           # ❌ 与"内耳眩晕症"语义重复
  - 记忆口诀            # ❌ 自作主张——summary 里没出现，丢弃
```

**分类节点正模式**（来自 `酰胺类中枢兴奋药.md`）：

```yaml
tags:
  - 酰胺类              # 分类名 ← summary 加粗
  - γ-氨基丁酸衍生物     # 本质 tag ← summary 加粗
  - 吡拉西坦            # 重点子代表药 ← summary 加粗（代表药之一）
  - 脑代谢改善          # 功能作用机制 ← summary 加粗
```

##### 5.11.4.5 兜底自取的汇报要求

| 抽取来源 | 汇报措辞 |
| --- | --- |
| md 文字 `**加粗**` 标记 | "来自 `**加粗**` 标记：`H1受体激动剂`、`内耳眩晕`" |
| summary 上下文（无标记但有该词） | "来自 summary 上下文（无标记但可检索）：`微循环改善`" |
| AI 兜底自取 | "**AI 兜底自取**：`XXX`（基于 summary 上下文，未在原资料中显式标注）" |

### 5.12 口诀双轨制（独立节点 + summary 内嵌）

口诀（mnemonic）必须**双轨呈现**，缺一不可：

1. **独立 `mnemonic` 节点**：按 §3.4 / §5.4 决定是否独立成节点；独立时由**口诀节点自身**的 `edges_out` 写 `part_of → 主知识节点`（参见 §5.15 + §10.4）。理由：新增口诀时只新增口诀 md，不必回去修改主知识节点的 `edges_out`。
2. **同时写入对应主知识节点的 `summary`**：让用户即使不展开图谱也能直接看到口诀。

| 口诀类型      | 独立 `mnemonic` 节点                    | 同时写入…的 `summary`                         |
| --------- | ------------------------------------ | -------------------------------------- |
| **药物口诀**  | ✅ 独立节点（如 `倍他司汀口诀.md`）             | 该**药物**节点的 `summary.short` 末尾           |
| **分类口诀**  | ✅ 独立节点（如 `酰胺类分类口诀.md`）            | 该**分类**节点的 `summary.short` 末尾；或 `summary.full` 中的【口诀】标注 |
| **章节级口诀** | ✅ 独立节点（如 `第一章核心口诀.md`）           | 该**节/章**节点的 `summary.short` 末尾 |

**写入位置约定**：

- 药物口诀 → 写入该药物 `summary.short` 末尾，**用 `；` 与前半段分隔**，或单独成段：

  ```yaml
  short: α受体拮抗剂，禁与β受体拮抗剂合用。口诀：**α拮抗扩血管，麦角林最典型**。
  ```

  或更详细的：

  ```yaml
  short: α受体拮抗剂，禁与β受体拮抗剂合用。

    口诀：α拮抗扩血管，麦角林最典型。
  ```

- 分类口诀 → 写入该分类 `summary.short` 末尾，类似规则。

**反模式**：

1. ❌ 只有独立口诀节点，没在主知识节点的 `summary` 同步内嵌——用户看不到。
2. ❌ 只在主知识节点 `summary` 里写口诀，没建独立 `mnemonic` 节点——图谱里没有这条口诀的边。
3. ❌ 把药物口诀写到分类节点的 `summary` 里（口诀归属错位）。

| 表格所在位置                  | 父节点                        |
| ----------------------- | -------------------------- |
| **章节级**对比表（多个分类下的药物横向比较） | **节节点**（如"第四节 抗记忆障碍及改善神经功能药"） |
| **分类内**对比表（同一分类下多个药物）    | 该**分类节点**（classification）   |
| **药物级**对比表（单药物内部项目对比）   | 该**药物节点**（medication）       |

### 5.14 同名节点文档的重写规则

> **两层规则区分**：
> - **frontmatter（YAML 块）**：严格遵守用户资料，不可擅作主张——见 §5.8（summary 填写）、§5.11（格式）。
> - **正文（`# …` 之后的 Markdown 正文）**：宽松处理——保留即可，不强制清空。
>
> 原因：frontmatter 是图谱的结构化元数据（字段决定节点在图谱中的位置、关系、检索结果），必须精确；正文是非结构化描述，用户通常不会逐字段提供，且对图谱结构无影响。

**触发条件**：发现已存在同名（或同 `id`）的 `.md` 节点文档，需要用新资料重写。

#### 5.14.1 frontmatter 字段（严格重写）

按以下表格处理 frontmatter 各字段，**与 §5.8 summary 字段填写原则同源**：

| 字段                       | 重写时怎么处理                                              |
| ------------------------ | ----------------------------------------------------- |
| `data.id`                | **保留原值**（保持 ID 不变以免破坏所有指向该节点的边）                     |
| `data.label`             | **保留原值**（除非用户明确要求改名）；必须是**中文**                           |
| `data.location`          | **可参考**（仅作为目录位置依据，不强制沿用）                             |
| `data.essence`           | **不沿用**，按新资料重新判定                                     |
| `data.depth`           | **自动推导**，无需沿用                                    |
| `data.tags`              | **不沿用**，按 §5.11.4 重新抽取                                 |
| `data.edges_out`         | **重建**（按新资料重建，不保留旧边，除非用户明确指示）                       |
| `summary.short`          | **不沿用旧文本**，按用户新资料重写                                  |
| `summary.full`           | **不沿用旧文本**，按用户新资料重写（用户未提供的部分必须留空，不擅自补）                 |

**铁律**：

1. ❌ **`id` 必须是英文**，不得使用中文拼音或中文汉字；`label` 必须是中文。
2. ❌ **不**因"沿用比重新写安全"就保留旧值——除非该字段不在本表"不沿用"列。
2. ❌ **不**因"旧文档里有合理内容"就复制粘贴到新文档——必须由用户提供为准。
3. ❌ **不**因"用户没说就按惯例补"——见 §5.8。
4. ✅ 用户资料缺失时（如只给药名没给临床信息），**主动列出哪些字段无资料、等待用户补充**，而不是擅自补默认值。

#### 5.14.2 正文（宽松保留）

| 场景                                              | 正文处理                                       |
| ----------------------------------------------- | ------------------------------------------ |
| 已有同名节点，**正文已有内容**，未要求重写正文                  | **保留旧正文**，不强制清空、不强制重新组织                 |
| 已有同名节点，**正文已有内容**，用户明确要求"重写正文"             | 按用户提供的新正文替换；用户未提供的段落保留或留空（视用户原话判断）       |
| 已有同名节点，**正文已有内容**，AI 判断旧正文与新 frontmatter 矛盾 | **不动正文**（frontmatter 严格、正文宽松——矛盾由用户裁决）  |
| **新增节点**，用户**未提供正文**                          | **正文留空**——不写占位符、不写"待补充"、不写任何"AI 润色段" |
| **新增节点**，用户**提供了正文**                           | 原样写入，不二次润色（参见 §5.8 正模式 2）                |

**铁律**：

1. ❌ **不**因"旧正文存在就更顺手清空"——用户没要求就保留。
2. ❌ **不**因"frontmatter 重写了就显得正文过时"就清空正文——这是两套规则，不要混用。
3. ❌ **不**因为新增节点没正文就写一段"占位说明"或"AI 自动生成的简要描述"。
4. ✅ 新增节点无正文时，文件中可以**完全不包含**正文区（即 frontmatter 后直接 EOF；或 frontmatter 后只留一个空行）。

#### 5.14.3 汇报约定

重写同名节点时，在最终汇报里**分层汇报**：

- **frontmatter 部分**（按 §5.14.1 表格逐字段说明）：
  - "沿用"（id / label / location）
  - "用户提供"（short / full 哪几段）
  - "未提供，留空"（哪些字段用户没给）
  - "未提供，等待补充"（哪些字段用户没给且影响图谱完整性）
- **正文部分**（按 §5.14.2 表格说明）：
  - "保留旧正文" / "按用户新正文替换" / "正文留空（用户未提供）"

若 frontmatter 中用户未提供的字段**影响图谱结构性正确性**（如 `edges_out` 缺失导致节点无入边/无出边），**主动提醒**用户补充，而不是擅自建一条占位边。

#### 5.14.4 判断锚点（self-check）

| 问自己                              | 答案                                    |
| -------------------------------- | ------------------------------------- |
| 我要改的是 frontmatter 字段？          | 默认答案：**不能擅自动手**——必须等用户提供；缺失就留空并提醒       |
| 我要改的是正文？                       | 默认答案：**能不动就不动**——除非用户明确要求重写            |
| 我面对的是新增节点，用户没给正文？              | 默认答案：**正文留空**，不写任何内容                    |
| 如果我不在场，用户能否接受我写进文件的每一字（frontmatter）？ | 不能 → 留空、汇报、等待；能 → 写                  |

### 5.15 `edges_out` 字段填写原则

> 与 §5.8（summary）、§5.14（重写）一起，构成"frontmatter 三铁律"——但 `edges_out` 是其中**最宽松**的一节：边类型受限于 frontmatter 规定的 6 种，**具体 reason 措辞和挂边判断 AI 可发挥主观能动性**。
>
> 与 §5.8（summary 严格）和 §5.14（重写严格）形成对比——本节是"AI 可主动判断"区，但有 3 条铁律。

#### 5.15.1 边方向铁律：每个节点自管自己的 `edges_out`

**核心**：所有 `edges_out` 都表示**"这个节点向外辐射的引用关系"**。任何关系的发起方都在自己的 md 文件里写。

| 方向规则                       | 由谁写                                |
| -------------------------- | ---------------------------------- |
| **类-类层级**（子类 → 父类）          | 子类写 `subclass_of → 父类`             |
| **局部-整体**（局部 → 整体）          | 局部写 `part_of → 整体`                |
| **个体-类**（实例 → 类别）          | 实例写 `instance_of → 类别`            |
| **辅助学习**（口诀 → 主知识）   | **辅助节点**写 `part_of → 主知识节点`       |
| **等价/互斥**（双向语义）            | **任一侧**写 `equivalent_to` / `disjoint_with → 对方`（存一条即可） |

**禁止**：

1. ❌ 父节点（子类/上层）写一堆 `edges_out` 指向子节点——新增子节点时必须回来改父节点。
2. ❌ 子节点写 `subclass_of` → 父节点的同时又写 `part_of` → 父节点——同方向重复。
3. ❌ 双向边正反都写（同一对节点同时 A→B 和 B→A 两条 `subclass_of` / `part_of`）——单向即可。
4. ❌ 用 `subclass_of` 来表达 `part_of`（"口诀属于药物的层级"是错的，口诀是局部-整体）。
5. ❌ 把节点之间的引用全部塞到父节点里（错把"全局索引"当成 `edges_out`）——这是数据冗余和编辑耦合。

**正模式**：

1. ✅ **新增子节点时**：只需新建该子节点的 md 文件，写自己的 `subclass_of` / `part_of → 父节点`。**不必回去修改父节点**。
2. ✅ **新增口诀节点时**：只需新建口诀 md，写 `part_of → 主知识节点`。**不必回去修改主知识节点**。
3. ✅ **新增对比表节点时**：只需新建表 md，写 `part_of → 父分类/节节点`。
4. ✅ **互斥/等价关系单边写**：苯二氮䓬类 `disjoint_with` 非苯二氮䓬类 写一条即可，渲染端补双向视觉。

#### 5.15.2 边类型选择决策表

| 关系                          | 用什么 type | 方向（写在谁的文件里）  | reason 措辞规范               |
| --------------------------- | -------- | ------------ | ----------------------- |
| 分类 X 是分类 Y 的子类              | `subclass_of` | 分类 X 写       | `一种{分类Y}`               |
| 药物 A 属于分类 X（药物→分类亚类）       | `instance_of` | 药物 A 写       | `一种{分类X}`               |
| 章节 第一节 是 章节点的一部分           | `part_of` | 第一节写         | `{章名}的一部分`              |
| 不良反应/机制/适应症 是 药物画像的一部分      | `part_of` | 内容节点写        | `{药物画像}的一部分`           |
| 口诀节点 ↔ 药物/分类               | `part_of` | **口诀节点**写     | `{主知识名}记忆口诀`            |
| 注意/提示节点 ↔ 药物                | `part_of` | **注意节点**写     | `{药物名}注意事项`             |
| 对比表节点 ↔ 分类/节                | `part_of` | **对比表节点**写    | `{分类/节名}药物对比`           |
| 药物 A 易混于药物 B（互斥）           | `disjoint_with` | **任一侧**写     | `与{药名}互斥`               |
| 药物 A 等价于 药物 B（别名）          | `equivalent_to` | **任一侧**写     | `等价于{药名}`               |

#### 5.15.3 `reason` 措辞规范

- **必填**：所有 `edges_out` 条目都必须有 `reason`（reason 不可空，必须写具体药学语义）。
- **AI 可发挥主观能动性**：reason 措辞不必逐字按用户原文，可基于上下文重新组织。
- **最低要求**：
  - 必须包含**具体对象**（药名 / 分类名 / 疾病名 / 机制名）——不能是"治疗""相关""适用"等空泛词。
  - 必须能独立成句——读者看到 reason 即可理解这条边的语义。
- **建议模板**（按 type 提供自然语言）：
  - `subclass_of`：`属于{上级类名}`，如 `一种苯二氮䓬类`
  - `instance_of`：`{动作}{对象}`，如 `治疗癫痫持续状态`、`激动GABA_A受体`、`导致粒细胞缺乏`
  - `part_of`：`{主知识名}{角色}`，如 `吡拉西坦记忆口诀`、`镇静催眠药的一项`、`某节总结`
  - `disjoint_with`：`与{对方}互斥`，如 `与吡拉西坦互斥（同为酰胺类但不可同用）`
  - `equivalent_to`：`与{对方}等价`，如 `与苯二氮䓬等价（译名一致）`

**正模式**：

```yaml
edges_out:
  - target: strict-amide
    type: subclass_of
    reason: 一种酰胺类中枢兴奋药
  - target: med-piracetam
    type: part_of
    reason: 吡拉西坦记忆口诀
  - target: med-oxiracetam
    type: disjoint_with
    reason: 与吡拉西坦互斥（同为酰胺类但不可同用）
```

**反模式**：

```yaml
edges_out:
  # ❌ 父节点写一堆子节点——耦合、不可扩展
  - target: med-piracetam
    type: subclass_of
    reason: 属于本分类
  - target: med-aniracetam
    type: subclass_of
    reason: 属于本分类

# ❌ 辅助方反向——新增口诀时需改药物
# ❌ reason 空泛
  - target: med-piracetam
    type: part_of
    reason: 相关
```

#### 5.15.4 占位边禁止

- ❌ **不得**为"看起来完整"就建占位边（如 `subclass_of → adr-unknown` 占位未知 ADR）。
- ❌ **不得**为尚未确认的关系预先建边（如用户只说"可能与 X 相互作用"就建 `instance_of → X`）——遇到不确定的，明确告知用户"该关系需要确认，是否建边"。

#### 5.15.5 汇报约定（edges_out 部分）

创建/重构一个节点时，汇报里**必须**列出 `edges_out` 每条边的来源：

| 来源                  | 汇报措辞                   |
| ------------------- | ---------------------- |
| 用户明确告知              | "用户提供：…→{target}（{reason}）" |
| AI 基于用户资料推断（边类型 / reason 措辞） | "AI 推断：…→{target}（{reason}）——基于用户提供的'{用户原话关键句}'" |
| 保留原值                | "沿用旧边：…→{target}（{reason}）" |
| 未提供 / 留空            | "未提供，留空：应挂 …→{target}（待用户确认）" |

#### 5.15.6 判断锚点（self-check）

| 问自己                                                | 答案                                              |
| -------------------------------------------------- | ----------------------------------------------- |
| 这条边写完后，**新增一个新子节点 / 辅助节点时**，是否需要回到这条边的发起方文件里改 `edges_out`？ | **不需要** → 写法正确；需要 → 方向反了或位置写错              |
| 这条边的 `edges_out` 写在**子类 / 局部 / 业务提供方**那一侧的 md 文件里吗？ | 是 → 正确；否 → 改为子类/局部那一侧                          |
| 我要用 `subclass_of` 还是 `part_of`？                   | `subclass_of` = 种类归属；`part_of` = 局部-整体 |
| reason 是否包含具体对象？                                   | 是 → 正确；否 → 补具体名词                                |
| reason 是否和用户原话差距过大？                                | 差距过大 → 汇报里告知用户"措辞偏离了原意"                     |

## 九、YAML 多行字符串规范（block scalar 必须）

### 9.1 规则

**所有可能跨行的字符串字段，必须用 YAML block scalar 标记 `|` 或 `>`，禁止靠纯缩进实现多行。**

适用范围（与本项目相关的字段）：

- `summary.full` — 节点完整摘要，最常包含表格、列表、对比点
- `summary.short` — 当摘要较长或含换行时
- `description` / `note` / `reason` — 任意自由文本字段

### 9.2 错误示例（绝对禁止）

```yaml
summary:
  full:                                   # ← plain scalar，YAML 1.2 不允许跨行
      蛋白质类药（重组XX，XX单抗）药物特点

      | 项目 | 内容 |
      | ---- | ---- |
      | 给药途径 | 皮下注射、静脉注射 |
```

**症状**：所有真实换行被自动折叠成单个空格，解析结果为：

```
"蛋白质类药...药物特点 | 项目 | 内容 | | ---- | ---- | | 给药途径 | 皮下注射..."
```

→ 节点面板里表格渲染失败（合并成一行），Markdown 解析器无法识别 GFM 表格语法。

### 9.3 正确示例（必须遵守）

```yaml
summary:
  full: |                                 # ← 加 `|` 标记，让 YAML 按 literal block scalar 解析
      蛋白质类药（重组XX，XX单抗）药物特点

      | 项目 | 内容 |
      | ---- | ---- |
      | 给药途径 | 皮下注射、静脉注射 |
```

→ 解析结果保留所有 `\n`，Markdown 表格正常渲染。

### 9.4 关键细节

| 关注点 | 说明 |
| --- | --- |
| 标记字符 | `|` = literal（保留所有换行，推荐）；`>` = folded（折成单行再换行，少用） |
| 缩进要求 | block scalar 的 body 缩进必须**严格大于** key 的缩进至少 1 格 |
| 单行字符串 | 如果字符串就是一行，**无需**加 `\|`（plain scalar 不会折叠）。仅当**实际跨行**时才必须加 |
| 字段白名单 | 仅在 `summary.full` / `summary.short` / `description` / `reason` / `note` 等自由文本字段适用；`id` / `label` / `essence` 等结构字段**永远单行**，不要加 `\|` |

### 9.5 为什么这条规则存在

YAML 1.2 spec 明确规定：plain scalar（无引号、无 `|`/`>` 标记）**不允许包含真实换行**——任何 newline 都会被解析器当作 fold 处理（折成单个空格），这是 spec 强制行为，不是库 bug。本项目使用 `yaml` 库（https://github.com/eemeli/yaml）严格遵循该 spec。

因此**写作者必须显式标记 block scalar**，不能依赖缩进让解析器"猜到"你想跨行。

### 9.6 验证方法

新增/编辑节点后，跑一遍：

```bash
node -e "const {parse}=require('yaml');const fs=require('fs');const m=fs.readFileSync(process.argv[1],'utf8').match(/^---\\r?\\n([\\s\\S]*?)\\r?\\n---/);console.log(JSON.stringify(parse(m[1]).data.summary,null,2))" 你的文件.md
```

看输出的 `full` 字段——如果内容里**含有 `\n`**，说明表格行独立成行，渲染正确；如果全部挤成一行（看不到 `\n`），说明漏写了 `|`，需要补上。

### 9.7 历史教训

- **蛋白质类药（重组XX，XX单抗）特点总结**（2026-09 初版）——`summary.full` 因漏写 `|`，表格被折叠成单行，节点面板里表格不可见。修复：在 `full:` 后加 `|`，一行字符的修改。
- **抗风湿药节 7 个 DMARDs**（双醋瑞因 / 托法替布 / 来氟米特 / 柳氮磺吡啶 / 甲氨蝶呤 / 羟氯喹 / 金诺芬，2026-09 初版）——`summary.full` 用了 `(1)(2)(3)(4)` 的纯文本编号格式，没有用 `【标签】` 分段，也没有用 markdown 列表/粗体，节点面板里整段文字读起来像糊墙。修复见 §10。
- **第三节 抗痛风药 — 16 个文件命名**（2026-09 初版）——全部用英文 `data.id`（`med-allopurinol-y2-02-03.md` 等）作为文件名，导致目录里全是英文字符串，与样板（第一章第四节用中文 label 命名）不一致，文件查找困难。修复：全部重命名为中文 label（`别嘌醇.md`、`苯溴马隆.md` 等）。
- **sitemap.xml 手动同步极易遗漏**（2026-09 末版）——节点重命名后 sitemap URL 未同步，搜索引擎指向不存在路径。修复：`vite.config.ts` 的 `contentManifestPlugin()` 在每次 `buildStart` 和 `handleHotUpdate`（.md 文件变化）时自动扫描 `public/content/` 重建 sitemap，永远与文件系统一致。**无需再手动维护。**

**约定强化**：文件名 = `data.label`（中文），`data.id` = 英文/拉丁文 ID（用于图的 id 寻址、sitemap、edges_out 引用）。两者分工，不可混用。


## 十、临床内容格式规范（【标签】格式）

### 10.1 规则

**所有 `essence: medication` / `strict-class` / `umbrella-class` 节点的 `summary.full` 必须用「【标签】 + 段落」格式分段，禁止使用 `(1)(2)(3)` 半角括号编号，禁止把整段文字塞进一段不换行。**

### 10.2 标签清单（按使用频率排序）

| 标签 | 何时使用 | 样板 |
| --- | --- | --- |
| 【药理作用】 | 机制、受体、靶点 | `吡拉西坦.md` |
| 【适应症】 | 适用疾病、用法用量要点 | `吡拉西坦.md`、`托法替布.md` |
| 【不良反应】 | ADR、严重副作用、监测要求 | `双醋瑞因.md` |
| 【禁忌】 | 妊娠/哺乳/严重肝肾损伤等绝对禁用 | `来氟米特.md` |
| 【相互作用】 | 与其他药物的相互作用、酶系影响 | `托法替布.md`、`双醋瑞因.md` |
| 【药代动力学】 | 吸收/分布/代谢/排泄、半衰期 | `柳氮磺吡啶.md` |
| 【临床应用注意】 | 特殊人群、起效慢、监测指标等注意事项 | `羟氯喹.md`、`金诺芬.md` |

> 标签可以增减（如 `【用法用量】`、`【特殊人群】`），但**每段必须以 `【...】` 起头**，让阅读者扫一眼就知道段落主题。

### 10.3 错误示例（绝对禁止）

```yaml
summary:
  full: |-
    (1)抑制合成嘧啶的二氢乳清酸脱氢酶，使活化B细胞的生长受抑制
    (2)适应证：①适用于成人类风湿关节炎(有改善病情作用)、狼疮性肾炎；②半衰期长，间隔24h给药一次；③开始治疗的最初3日给予负荷剂量50mg/d，之后维持治疗10mg/d或20mg/d
    (3)妊娠期、哺乳期、严重肝、肾损伤者禁用
    (4)慎与利福平合用，以免引起活性代谢产物浓度持续升高，增加药物中毒(尤其是肝损伤)的风险
```

**症状**：
- 没有视觉分段，整段糊在一起难读
- `(1)(2)(3)(4)` 编号 + ① ② ③ 嵌套 + 半角括号，视觉噪音大
- 重点词没有 `**加粗**`，扫不到核心信息
- 节点面板渲染后像一堵字墙

### 10.4 正确示例（必须遵守）

```yaml
summary:
  full: |
    【药理作用】抑制合成嘧啶的**二氢乳清酸脱氢酶**，使活化 B 细胞的生长受抑制。

    【适应症】
    - 适用于**成人类风湿关节炎**（有改善病情作用）、**狼疮性肾炎**。
    - **半衰期长**，间隔 24h 给药一次。
    - 开始治疗的最初 3 日给予负荷剂量 **50mg/d**，之后维持治疗 **10mg/d 或 20mg/d**。

    【禁忌】妊娠期、哺乳期、严重肝、肾损伤者禁用。

    【相互作用】慎与利福平合用，以免引起活性代谢产物浓度持续升高，增加药物中毒（尤其是肝损伤）的风险。
```

**好处**：
- 每段 `【标签】` 起头，扫一眼就知道主题
- 关键词 `**加粗**`，重点一眼可见
- 多项用 markdown 列表 `- `，视觉清爽
- 段落间空行分隔，节点面板像文档不像字墙

### 10.5 markdown 用法要点（仅在本字段允许）

| 元素 | 用法 | 示例 |
| --- | --- | --- |
| 段落标题 | `【标签】` 起头 + 空行分段 | `【药理作用】...` |
| 关键词加粗 | `**两个星号**`（中英文/数字之间加空格） | `**半衰期长**`、`**50mg/d**` |
| 列表 | `- ` 起头（英文短横 + 空格） | `- 适用于 RA、SLE。` |
| 表格 | GFM `\| 列 \| 列 \|` 格式（见 §9） | `蛋白质类药特点总结.md` |
| 内联强调 | 避免 `__下划线__` / `*单星号*`（与中文标点视觉冲突） | — |

**禁止**：
- `#` `##` `###` 标题（会破坏节点面板布局）
- HTML 标签（`<br>` 等）
- 整段纯文本不换行（即使加了 `|` block scalar 也会糊墙）

### 10.6 单字段 vs 多段落的判断

| 内容量 | 推荐做法 |
| --- | --- |
| 1–2 句简短摘要 | 单段 + `【标签】` 即可，如 `【适应症】用于 X、Y。` |
| 3–4 句中等 | 按主题拆 2–3 个 `【标签】` 段 |
| 5+ 句大段临床 | 必拆 4 个以上 `【标签】` 段，每段不超过 3–4 行 |
| 含子项列表 | 用 `- ` markdown 列表 |

### 10.7 验证方法

写完后视觉检查：
1. 在 IDE 里用 `Cmd+Shift+V` 预览 markdown，确认每段独立成段、表格行独立成行
2. 跑 `npx vitest run` 确保 YAML 解析不报错
3. 起 dev server `npm run dev` 在浏览器里看节点面板实际渲染效果

### 10.3 边类型使用

整个样板仅使用 3 种边类型：

| 边类型 | 发起方（写在谁的文件里） | 数量 | 说明 |
| --- | --- | --- | --- |
| `instance_of` | **子节点**（medication / umbrella-class / section / chapter / book） | 20 条（每个非根节点 1 条） | 层级归属：药物→分类、分类→节、节→章、章→书 |
| `subclass_of` | **严格分类节点**（strict-class） | — | 严格药理分类细分时使用 |
| `part_of` | **辅助节点**（mnemonic 口诀） | 4 条（每个口诀 1 条 `part_of→` 主知识） | 口诀→主知识、总结→节 |

不使用 `link`/`relate`/`branch`/`contrast` — 临床关系全部在 `summary.full` 文本中。

### 10.4 关键设计决策

1. **无冗余空模块**：不建"分类与代表药品"和"临床用药评价"空模块。层级链直接章→节→分类→药物。
2. **临床内容在 summary.full**：药理/适应症/禁忌/相互作用全部写入 summary.full 的【标签】格式文本。
3. **口诀与主知识用 `part_of` 边**（不是由药物节点发起）：口诀节点在自己的 md 文件里写 `edges_out: - target: med-betahistine, type: part_of`。理由：新增一个口诀时只需新增口诀 md，不必回去修改药物节点的 `edges_out`。这与 §5.15 的"自管 `edges_out`"原则一致。

> **关于 depth 自动推导**：因 depth 现在是 BFS 推导，连接方式（`part_of` vs `instance_of`）直接决定口诀与主知识的同层 / 父子关系。口诀用 `part_of` 指向药物 → 两者同 BFS 深度 → 视觉上同级，自然呈现"平行学习辅助"的关系。无需人工赋 level。
