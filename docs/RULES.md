# 节点重构规则

> 适用范围：在已有图谱上，将旧版 frontmatter（12 种边、6 种 essence、无 level）迁移到新版规范（6 种边、11 种 essence、6 级 level），以及迁移完成后的结构性清理（合并、拆分、骨架补齐）。
>
> 配套文档：[frontmatter.md](./frontmatter.md) — 字段定义与视觉编码规范（权威来源）。
>
> 原则：忠实保留药学语义，不丢边、不丢正文；边类型迁移与内容合并分离提交。

***

## 一、迁移总览

当前图谱有 **1083 个 .md 文件**，使用 12 种旧边类型和 6 种旧 essence 值，无 `level` 字段。需要迁移到新规范：

| 维度       | 旧版                                                                                                                   | 新版                                                  | 迁移方式                      |
| -------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | ------------------------- |
| 边类型      | 12 种（isa/has/treats/relates/prerequisite/mechanism/activates/sibling/specializes/causes/contraindicates/metabolizes） | 6 种（parent/branch/link/relate/support/contrast）     | 批量脚本 + 人工校验               |
| essence  | 6 种（medication/module/illness/concept/process/section）                                                               | 11 种（新增 classification/mnemonic/summary/table/note） | 按语义逐个重分类                  |
| level    | 不存在                                                                                                                  | 1-6 级                                               | 按 location 层级批量赋值 + 人工微调  |
| ADR-0001 | isa/has 方向规则                                                                                                         | parent/branch 方向规则                                  | isa→parent，has→branch 或删除 |

## 二、边类型迁移映射表

每条旧边必须按下表迁移到新边类型。**具体药学语义写进** **`reason`，不再各占一个** **`type`。**

| 旧边类型              | 数量   | 新边类型         | reason 写法             | 迁移说明                                               |
| ----------------- | ---- | ------------ | --------------------- | -------------------------------------------------- |
| `isa`             | 1096 | `parent`     | 保留原 reason            | 层级归属，子→父方向不变                                       |
| `has`             | 598  | `branch` 或删除 | 保留原 reason            | 父→子的 has：改为 branch；子→父的反向 has：删除（已由子节点的 parent 覆盖） |
| `treats`          | 345  | `link`       | `reason: 治疗{疾病名}`     | 药物→疾病的明确关系                                         |
| `relates`         | 318  | `relate`     | 保留原 reason            | 一般关联，兜底关系                                          |
| `prerequisite`    | 261  | `link`       | `reason: 前置依赖——{说明}`  | 学习前置关系，是明确知识关系                                     |
| `mechanism`       | 114  | `link`       | `reason: 机制——{说明}`    | 药物→机制的明确关系                                         |
| `activates`       | 14   | `link`       | `reason: 激动{靶点}`      | 药物→靶点的明确关系                                         |
| `sibling`         | 12   | `relate`     | 保留原 reason            | 同级关联                                               |
| `specializes`     | 9    | `link`       | `reason: 特化——{说明}`    | 特化/衍生关系                                            |
| `causes`          | 5    | `link`       | `reason: 导致{不良反应}`    | 药物→ADR 的明确关系                                       |
| `contraindicates` | 3    | `link`       | `reason: 禁忌——{人群/状态}` | 药物→禁忌的明确关系                                         |
| `metabolizes`     | 1    | `link`       | `reason: 代谢——{说明}`    | 药物→代谢酶的明确关系                                        |

### 迁移后的 6 种边类型语义

> **方向判定规则**：所有边的方向都**由 `level` 数字大的节点指向 `level` 数字小的节点**（子→父）。同 `level` 之间用 `contrast` 双向或 `relate` 单向。
>
> **业务主动方例外**：`support` / `link` 边允许由"业务主动方 / 提供方"发起（如口诀节点发起 `support→药物`），不强制 level 大→小——以"新增节点时不必回来修改其他节点"为准。
>
> **理由**：所有 `edges_out` 都是"这个节点向外辐射的引用关系"，新增一个子节点只需要新建它自己的 md 文件，**不必修改任何已有节点的 `edges_out`**。这是文档自治的前提。

| 边类型        | 回答什么             | 方向（`edges_out` 写在…这边）       | 视觉       | 典型场景                          |
| ---------- | ---------------- | ------------------------- | -------- | ----------------------------- |
| `parent`   | "A 属于 B 的层级"     | 子节点（level 大）写 `parent→` 父节点 | 灰色实线无箭头  | 药物→分类→节→章（永远是子→父）            |
| `branch`   | "A 展开为 B"        | 父节点（level 小）写 `branch→` 子节点 | 蓝色实线无箭头  | **实际不使用**——level 已承载层级，branch 与 parent 二选一 |
| `link`     | "A 和 B 有明确的药学关系" | 业务主动方（提供方）发起                | 绿色实线三角箭头 | 治疗/导致/禁忌/机制/代谢（reason 承载具体语义）   |
| `relate`   | "A 和 B 有弱关联"     | 任意一方（推荐 level 大 / 提供方）     | 灰紫点线无箭头  | 同级关联、一般参考                     |
| `support`  | "A 配一个学习辅助 B"    | **辅助方**（口诀、注意、对比表）发起       | 橙色虚线三角箭头 | **口诀节点**写 `support→药物/分类`，**对比表**写 `support→分类/节` |
| `contrast` | "A 和 B 需要横向对比"   | 任意一方（双向视觉）                  | 紫色虚线双向箭头 | 易混药物对比（两侧互写 `contrast→` 对方，或单边写、渲染端补双向） |

### 关键迁移规则

1. **`has`** **的双向清理**：旧版 A has→ B 和 B has→ A 同时存在的双向配对，迁移后只保留 `branch`（父→子方向），删除子→父的反向边。**实际落地时** `branch` 与 `parent` 二选一，统一用 `parent` 子→父方向。
2. **`reason`** **不可空**：迁移到 `link` 的边，如果原 reason 为空，必须补写具体语义（如 `reason: 治疗癫痫`）。具体措辞 AI 可基于用户资料判断，但必须明确（不得写"治疗""相关"这种空泛词）。
3. **`parent`** **和** **`branch`** **不共存**：同一对节点不能同时有 `parent` 和 `branch`。统一用 `parent`，方向子→父。
4. **`support`** **是新关系**：旧版口诀/注意内嵌在正文里没有边。迁移时，如果口诀/注意已升级为独立节点（essence: mnemonic/note），**由辅助节点（口诀/注意）发起 `support` 边指向主知识节点**（不是反过来）。理由：新增口诀时只新增口诀 md 即可，不必修改药物 md。

## 三、essence 迁移

### 3.1 保留不变的 essence（6 种，直接沿用）

| 旧 essence    | 新 essence    | 说明                                          |
| ------------ | ------------ | ------------------------------------------- |
| `medication` | `medication` | 不变                                          |
| `module`     | `module`     | 不变                                          |
| `illness`    | `illness`    | 不变                                          |
| `concept`    | `concept`    | 不变（但需逐个检查是否应改为 `notion` 或 `classification`） |
| `process`    | `process`    | 不变                                          |
| `section`    | 见下           | 需逐个重分类                                      |

### 3.2 `section` 重分类

`section` 是位置标记（"这是第几节"），不是知识本体。按实际语义重分类：

| section 节点的实际内容      | 迁移到              | 理由            |
| -------------------- | ---------------- | ------------- |
| 章节入口（如"第二节 抗癫痫发作药物"） | `module`         | 是结构容器，不是独立知识点 |
| 分类标准（如"按作用机制分类"）     | `classification` | 本质是分类依据       |
| 学习认知单元（如"用药监护"）      | `notion`         | 本质是学习性认知      |

### 3.3 `concept` 拆分检查

旧版 `concept` 是万能兜底。逐个检查，按新语义重新归类：

| concept 节点的实际内容   | 迁移到              | 理由                        |
| ----------------- | ---------------- | ------------------------- |
| 药物分类/分组标准         | `classification` | 本质是分类                     |
| 学习性认知单元（监护、评价、原则） | `notion`         | 本质是"怎么学/怎么用"              |
| 纯概念/术语（如"首过效应"）   | `concept`        | 保留不变                      |
| 口诀/记忆辅助           | `mnemonic`       | 独立后由**辅助节点自身**的 `edges_out` 写 `support → 主知识`（参见 §5.15）|
| 总结/归纳             | `summary`        | 独立后由**辅助节点自身**的 `edges_out` 写 `support → 主知识`（参见 §5.15）|
| 对比表格              | `table`          | 独立后由**辅助节点自身**的 `edges_out` 写 `support / contrast → 主知识`（参见 §5.15）|
| 注意/提示/笔记          | `note`           | 独立后由**辅助节点自身**的 `edges_out` 写 `support → 主知识`（参见 §5.15）|

### 3.4 新增节点类型的使用条件

以下 4 种新 essence 在旧版中不存在，迁移时**按需创建**：

| 新 essence  | 何时创建独立节点                 | 何时内嵌正文不建节点         |
| ---------- | ------------------------ | ------------------ |
| `mnemonic` | 覆盖多个药物/亚类的章级或模块级大口诀      | 单个药物的局部小口诀         |
| `summary`  | 整章/整节的核心总结，需要被多个节点引用     | 单个段落的临时小结          |
| `table`    | 需要在图谱中作为独立对比节点存在的横向对比表   | 药物正文内的 Markdown 表格 |
| `note`     | 需要在图谱中作为独立标签存在的【注意】/【提示】 | 药物正文内的一句话提醒        |

> **判断阈值**：如果这条口诀/总结/表格/注意在纸质思维导图上**有独立框/独立分支**，就建独立节点；如果只是考点旁边的标注文字，就内嵌正文。

## 四、level 赋值规则

`level` 是新字段，决定节点边框色。按以下规则批量赋值：

### 4.1 按 location 层级赋值（默认规则）

| location 最深层级  | level | 典型节点             |
| -------------- | ----- | ---------------- |
| `book`         | 1     | 学科总入口（药学专业知识一/二） |
| `part`         | 1     | 篇级入口             |
| `chapter`      | 2     | 章级入口（第一章 XXX）    |
| `section`      | 3     | 节级入口/伞形 module   |
| `item`         | 4     | 具体药物、疾病、机制       |
| 无 location 或更深 | 5-6   | 考点维度、口诀、注意等辅助节点  |

### 4.2 按 essence 微调（覆盖默认规则）

| essence          | 默认 level | 说明                     |
| ---------------- | -------- | ---------------------- |
| `module`         | 2-3      | 章级=2，节级=3              |
| `classification` | 3        | 分类节点一般在节级              |
| `medication`     | 4        | 具体药物                   |
| `illness`        | 4        | 具体疾病                   |
| `process`        | 4        | 具体机制                   |
| `concept`        | 4-5      | 核心概念=4，细分考点=5          |
| `notion`         | 5        | 学习认知单元                 |
| `mnemonic`       | 4-5      | 药物级口诀=4（与药物同级），模块级口诀=5 |
| `summary`        | 5-6      | 模块总结=5，章级总结=6          |
| `table`          | 5        | 对比表                    |
| `note`           | 5-6      | 药物级注意=5，末级标签=6         |

### 4.3 赋值优先级

1. 有 `location` 的节点：按 §4.1 的 location 层级赋值。
2. 无 `location` 但有 `essence` 的节点：按 §4.2 的 essence 默认赋值。
3. 两者都有但矛盾的：以 §4.2 的 essence 为准（因为 location 是教材目录，level 是思维导图结构，两者不一定一致）。

## 五、合并规则（沿用旧版，调整后保留）

### 5.1 核心原则

1. **语义不丢**：合并节点的正文必须全部内化进目标节点。
2. **边不丢**：合并前先确认入边；若 > 0，需先迁移边再删除。
3. **不重建已删节点**：合并提交只改源节点正文 + 删除源 md，不新增节点。
4. **schema 修复 vs 内容合并分离**：边类型迁移、essence 重分类、level 赋值各自独立提交。

### 5.2 合并候选识别（4 条信号）

| 信号                                                 | 含义         | 处置                     |
| -------------------------------------------------- | ---------- | ---------------------- |
| ① `in_deg == 0` 且 essence 非 `medication`/`illness` | 零散节点       | 优先就地扩伞形/节正文；无合并去向则直接删除 |
| ② 伞形 module 正文缺机制/口诀段，但同级伞形都有                      | 结构不对称      | 把 in\_deg=0 的零散节点内化进伞形 |
| ③ 伞形 module 正文已包含与同目录 concept 完全重复的内容              | 已合并但忘了删 md | 直接删除 concept           |
| ④ 节节点正文已包含与同目录 concept 完全重复的内容                     | 同上         | 同上                     |

**不视为合并候选**：

- `in_deg == 0` 但 essence 是 `medication` 或 `illness`（具体药物/疾病是图谱一等公民）

- `in_deg > 0`（有入边即被引用，需先迁移边再合并）

### 5.3 合并去向决策

1. **伞形 module 正文的对应段** — 零散 concept 的内容天然属于伞形语义。
2. **节节点正文的相关段** — 跨伞形总论性 concept 归节。
3. **直接删除** — 当节点纯粹是孤立冗余，无任何合并价值时。

### 5.4 新版变化：口诀/注意不再强制合并

旧版 REFACTOR-RULES §零 规定"口诀禁止独立成节点，必须内嵌"。**新版推翻此规则**：

- 口诀（`mnemonic`）、总结（`summary`）、表格（`table`）、注意（`note`）**可以独立成节点**。

- 判断标准：纸质思维导图上有独立框/独立分支的 → 独立；只是考点旁标注文字的 → 内嵌。

- 独立的口诀/注意节点**自身**用 `support` 边指向主知识节点（不是反过来）。详见 §5.15。

### 5.5 骨架边补齐（与合并正交）

当某章节的伞形 module in\_deg=0，但本来应该有 `parent` 边指向父级时，属骨架缺失而非过度拆分。

| 场景                      | 处置           |
| ----------------------- | ------------ |
| 节点零入度 + 有自身语义           | 合并到伞形/节正文    |
| 节点零入度 + 是骨架本身（伞形/药物/疾病） | 补 `parent` 边 |
| 节点零入度 + 是图入口（节、章、book）  | 不动           |

### 5.6 禁止冗余空模块

**不得创建纯视觉分区的空 wrapper 节点。** 每个节点必须有独立知识语义。

| 场景                           | 处置               |
| ---------------------------- | ---------------- |
| 创建"分类与代表药品"空模块（只做视觉分区，无独立语义） | ❌ 删除，药物直接挂到分类节点  |
| 创建"临床用药评价"空模块（只做视觉分区，无独立语义）  | ❌ 删除，临床评价下沉到药物节点 |
| 章级入口（有完整 summary + 语义）       | ✅ 保留             |
| 节级入口（有完整 summary + 语义）       | ✅ 保留             |

### 5.7 临床内容下沉模式

药物节点的临床内容（药理作用、适应症、禁忌、相互作用）**写入** **`summary.full`** **字段**，不拆成独立的 `link` 边。

```yaml
# ✅ 正确：临床内容在 summary.full
summary:
  short: 吡拉西坦是酰胺类代表药，改善脑代谢。
  full: >-
    【药理作用】作用于大脑皮质，激活神经细胞…
    【适应症】急慢性脑血管病所致记忆减退…
    【禁忌】锥体外系疾病、亨廷顿舞蹈症禁用…
    【相互作用】与华法林合用延长凝血酶原时间…

# ❌ 错误：为每个临床关系建独立边
edges_out:
  - target: some-disease
    type: link
    reason: 治疗
  - target: some-adr
    type: link
    reason: 导致
```

**何时用** **`link`** **边、何时用 summary.full？**

| 场景                     | 做法                |
| ---------------------- | ----------------- |
| 药物→疾病的对应关系需要图谱导航       | `link` 边 + 独立疾病节点 |
| 药物的药理/适应症/禁忌/相互作用是知识文本 | `summary.full` 内嵌 |
| 药物之间的相互作用需要可视化         | `link` 边          |
| 单纯的文字描述考点              | `summary.full` 内嵌 |

### 5.8 summary 字段填写原则

**`summary.full` 必须由用户手动提供，禁止 AI 自动填充。**

这是创建/重构节点文档时最容易越权的点，必须严格区分两类字段：

| 字段                | 创建时可自动初始化？   | 何时可填充/替换                                          |
| ----------------- | ------------- | ------------------------------------------------- |
| `summary.short`   | ✅ 可以（建议留空或简短占位） | 用户主动提供或确认后 **替换**（包括沿用旧值、手写改写、按用户指令重写）         |
| `summary.full`    | ❌ 禁止          | **仅当用户主动提供文本时** 才可写入；任何"智能补充"、"自动总结"、"按药理推断"都被禁止 |

**反模式（绝对禁止）**：

1. ❌ 创建新节点时由 AI 撰写 `full:` 内容，即使看起来"药理学上是正确的"。
2. ❌ 用通用占位字符串填充 `full:`（如 `"待补充"`、`"暂无内容"`），用户未要求时不得加占位。
3. ❌ 在用户改 `short` 时顺手重写 `full`，除非用户明确指示。
4. ❌ 把 `full` 拆成独立 `link` 边的同时，还往 `full` 字段里塞文字。两选一（见 §5.7）。
5. ❌ 用其它同章节、同分类节点的 `full` 文本进行"模板套用"——除非用户明确要求参照。

**正模式**：

1. ✅ 创建新节点时：若用户未提供 `full`，**该字段完全不写**（让 YAML 解析为 `undefined`，UI 自然隐藏"展开详情"按钮）。
2. ✅ 用户手写或口述一段内容并明确说"写入 full"：原样写入，不二次润色。
3. ✅ 用户明确要求"参考 X 节点的格式改写本节点的 full"：可以改写；否则不参照。
4. ✅ 用户只提供 `short`：仅替换/写入 `short`，**`full` 字段保持原样或不写入**，不留占位文本。
5. ✅ 用户提供多个药理点（如"作用：…用途：…禁忌：…"）：按用户给的标题分段写入 `full`，段落间用空行分隔（marked 会拆出多个 `<p>`）。

**汇报约定**：

- 创建/重构一个节点时，在最终汇报里**明示** `short`/`full` 两个字段分别做了什么（哪个是用户提供的、哪个是沿用旧的、哪个未改动、哪个为不写入）。
- 若用户未提供 `full`，汇报里必须出现 "未写 full / full 留空 / 待用户提供" 字样，便于用户知道该字段需要后续补充。

**判断锚点（self-check）**：

> "如果我不在场，用户能否接受我写进 `full` 的每一个字？"  
> 不能 → 删掉或留空；能 → 写。  
> 默认答案：**不能**，所以默认不写。

### 5.9 分类节点（classification）的内容归属

分类节点（`essence: classification`，如"酰胺类""乙酰胆碱酯酶抑制剂"）只承担**分类框架**作用：

| 内容类型                                     | 归属                                          |
| ---------------------------------------- | ------------------------------------------- |
| 分类的定义、范围、与其他分类的区别                     | 分类节点**自身**的 `summary.full`（用户手写补充时写入）     |
| 分类下每个具体药物的药理/适应症/禁忌/相互作用              | ❌ **不允许**写入分类节点；必须为**每个具体药物单独建立 `medication` 节点** |
| 该分类共用的学习要点（如"酰胺类共性：促进 Ach 合成"）          | 分类节点的 `summary.full`（用户手写补充时写入）              |
| 该分类下的对比表（药物横向对比）                       | 拆为独立 `table` 节点，父节点是该分类节点（详见 §5.13）           |

**反模式（绝对禁止）**：

1. ❌ 把"吡拉西坦的药理作用"写进"酰胺类"分类节点的 `summary.full` 里。药物内容必须下沉到药物节点。
2. ❌ 把多个药物的临床内容合并成一坨写进分类节点，再省略药物节点的 `summary.full`。
3. ❌ 把分类节点的 `summary.full` 当成"分类+所有药物摘要"的混合体。

**正模式**：

1. ✅ 分类节点只写分类自身的语义（"是什么""为什么这么分""共有特点"），正文简短。
2. ✅ 每个药物独立建 `medication` 节点，药物节点自己承载完整 `summary.full`。
3. ✅ 用户手写补充"该分类还需要一段总结性描述" → 写入分类节点 `summary.full`，作为分类的"上位总结"。
4. ✅ 用户未提供分类的总结性内容 → 分类节点 `summary` 可只写 `short`（或干脆不写）。

### 5.10 思维导图照片 → 节点字段的转录规则

用户提供思维导图照片（含荧光笔划线和手写补充）作为输入时，按以下规则把照片里的内容映射到节点字段：

| 照片里的内容                              | 写入哪                       |
| ----------------------------------- | ------------------------- |
| 图中**本来就有**的具体药物节点的正文内容（如药物名、药理描述） | 该药物节点的 `summary.full`     |
| 荧光笔划住的关键词 / 短语                      | **重组**为该药物节点的 `summary.short`（关键词用 `**…**` 加粗） |
| 用户**手写补充**的文字（不在原图里）               | 写入对应节点的 `summary.short`（手写补充是判断考点 / 重点的依据） |

**判定顺序（优先级从高到低）**：

1. **手写补充 > 图中原有**：用户手写的一定是新信息（强调 / 补充 / 订正），优先按手写内容写。
2. **荧光笔划住 > 普通印刷**：荧光笔划住的内容是该药物的核心考点，**重组成 short**，而非照搬原句。
3. **图中普通印刷**（非荧光笔）→ 该药物节点的 `full` 素材来源；非核心描述可酌情忽略（用户未要求全文录入时不录入）。
4. **同药物在多张照片出现** → 以"最新一张"为准；之前照片的差异向用户确认是否并入。

**正模式**：

1. ✅ 处理照片前，先用一句话告诉用户"我看到图里有 N 个药物节点、3 段手写补充，下面按 §5.10 转录"。
2. ✅ 转录 short 时，把"吡拉西坦是酰胺类中枢兴奋药"重新组织成"酰胺类中枢兴奋药，促进脑内**Ach↑**，激活、保护神经细胞"——关键词加粗。
3. ✅ 转录 full 时，**保留原图的【药理作用】【适应症】【禁忌】等段落标签**，按 §5.11 格式规范写。
4. ✅ 同一张照片里多个药物时，一次性处理完后**逐个汇报**哪个字段是手写、哪个是高亮重组、哪个是原文。

**反模式**：

1. ❌ 把荧光笔划住的字直接复制粘贴进 short，没有重组（用户高亮"组胺类、改善微循环血供"是为了强调，不是要原句）。
2. ❌ 把图中所有文字无差别全部复制到 full，忽略哪些是核心 / 哪些是噪音。
3. ❌ 在没有照片提供的节点上"按图谱惯例"自动推断 short——这是 §5.8 禁止的自动填充。

### 5.11 格式规范（short / full / tags / markdown 加粗）

#### 5.11.1 `summary.short` 格式

- 长度：**一句话或一段话**（建议 ≤ 80 字；超过 120 字应考虑拆分为 `short` + `full`）。
- 结构：**核心特点 + 核心用途**（或"作用 + 适应症"），用一句话说清"是什么 / 治什么"。
- 关键词：用 `**…**` 加粗（参见 §5.11.3 的关键词判定）。
- 句末：**不加句号以外的符号**（不用"。"以外的标点）。
- 不重复 `full` 已有的【适应症】段标签，避免 short 和 full 内容雷同。

✅ 例子（参见丁苯酞、倍他司汀等已落地节点）：

```yaml
short: 重构微循环、恢复能量代谢，芹菜过敏者禁用，用于轻中度**缺血性脑卒中**。
short: 组胺类药物，改善微循环血供，用于脑血管疾病和**内耳眩晕症**。
```

#### 5.11.2 `summary.full` 格式

- 多段结构，**前面必须标注清楚**章节标签，常用标签（不限于此，按实际内容选用）：
  - 【药理作用】【作用机制】
  - 【适应症】【用途】【临床应用】
  - 【禁忌】【禁用】【禁用人群】
  - 【不良反应】【副作用】【ADR】
  - 【相互作用】【配伍】
  - 【用法】【用法用量】【给药方案】
  - 【注意】【注意事项】【特殊人群】
  - 【药物过量】【解救】
- **段落之间必须空行**（YAML 块字符串内的空行）—— 否则 marked 不会拆出多个 `<p>`，所有内容会挤在一起（参见 `src/ui/markdown.ts` 中 `breaks: false` 的设定）。
- 每段开头**先写标签**，再写正文，例如 `【适应症】主要用于轻、中度急性缺血性脑卒中。`
- 标签内可以包含关键词的 `**加粗**`，但**不要在标签符号上做文章**（保留 `【…】` 的中文方括号样式）。
- 完整示例：

```yaml
full: |
  【药理作用】我国开发的新药，可重构缺血区微循环，恢复缺血区脑组织能量代谢，**抗脑血栓形成**和**抗血小板聚集**。

  【适应症】主要用于轻、中度**急性缺血性脑卒中**。

  【禁忌】对芹菜过敏者禁用（芹菜中所含的左旋芹菜甲素与本药化学结构相同）、有严重出血倾向者禁用。
```

#### 5.11.3 关键词判定与 `**加粗**`

加粗关键词的判断标准（满足任一条即可加粗）：

| 加粗条件                       | 例子                          |
| -------------------------- | --------------------------- |
| 药理学机制名词                    | **Ach↑**、**α受体拮抗**、**H₁受体** |
| 适应症（疾病名）                   | **急性缺血性脑卒中**、**内耳眩晕症**        |
| 禁忌关键人群 / 关键药名              | **芹菜过敏者**、**β受体拮抗剂**         |
| 用户**手写补充**时重点强调的词          | 用户笔记里的 `**…**` 直接保留        |
| 荧光笔划住的关键词                  | 照搬图中的高亮位置                   |
| 不良反应 / 严重警告                | 严重出血倾向、过敏等                  |

**不加粗的反例**：

- ❌ 把整段一句话加粗（失去重点）。
- ❌ 加粗"用于""是""的""和"等连接词。
- ❌ 同一句话里加粗超过 4 个词组（说明用户没提供足够信息，或 short 写得太长）。

#### 5.11.4 `tags` 字段

- **来源**：从 `summary.short` 和 `summary.full` 的内容里**抽取关键词**，不杜撰。
- **复用优先**：如果 `summary` 里已经有合适的关键词，**直接复用**，**不要自作主张另造同/近义词**（与 frontmatter §四一致）。
- **去重优先**：不写语义重复的标签——同一节点下不允许 `口诀` 与 `记忆口诀`、`禁忌` 与 `禁用`、`适应症` 与 `适用症` 等同/近义词并存。先出现则保留先出现的。
- 数量：3–6 个为宜；超过 6 个通常是因为分类过细，应合并。
- 写法：短词组（中文 2–6 字），首字母不大写，使用中文逗号分隔。
- 严禁把 `summary` 里没出现的概念放进 tags（否则图谱搜索时会出现"空标签命中"）。

```yaml
tags:
  - H1受体激动剂
  - 内耳眩晕
  - 微循环改善
```

**反模式**：

```yaml
tags:
  - H1受体激动剂        # ✅ 来自 summary 的 H1 受体
  - 组胺类药物          # ❌ 与"H1受体激动剂"近义，保留先出现的，丢弃这条
  - 内耳眩晕症          # ✅ 来自 summary 的"内耳眩晕症"
  - 眩晕耳鸣           # ❌ 与"内耳眩晕症"语义重复
  - 记忆口诀            # ❌ 自作主张——summary 里没出现，丢弃
```

**自取的最后机会**：只有当 `summary` 里完全找不到合适关键词时，才允许自取；但必须基于 `summary` 的上下文，不引入 `summary` 里没有的概念。**自取的 tag 必须在汇报里单独列出**。

### 5.12 口诀双轨制（独立节点 + summary 内嵌）

口诀（mnemonic）必须**双轨呈现**，缺一不可：

1. **独立 `mnemonic` 节点**：按 §3.4 / §5.4 决定是否独立成节点；独立时由**口诀节点自身**的 `edges_out` 写 `support → 主知识节点`（参见 §5.15 + §10.4）。理由：新增口诀时只新增口诀 md，不必回去修改主知识节点的 `edges_out`。
2. **同时写入对应主知识节点的 `summary`**：让用户即使不展开图谱也能直接看到口诀。

| 口诀类型      | 独立 `mnemonic` 节点                    | 同时写入…的 `summary`         |
| --------- | ------------------------------------ | ------------------------ |
| **药物口诀**  | ✅ 独立节点（如 `倍他司汀口诀.md`）            | 该**药物**节点的 `summary.short` 末尾 |
| **分类口诀**  | ✅ 独立节点（如 `酰胺类分类口诀.md`）           | 该**分类**节点的 `summary.short` 末尾 |
| **章节级口诀** | ✅ 独立节点（如 `第一章核心口诀.md`）           | 该**节/章**节点的 `summary.short` 末尾 |

**写入位置约定**：

- 药物口诀 → 写入该药物 `summary.short` 末尾，**用 `；` 与前半段分隔**，或单独成段：

  ```yaml
  short: α受体拮抗剂，禁与β受体拮抗剂合用。口诀：**α拮抗扩血管，麦角林最典型**。
  ```

  或更详细的：

  ```yaml
  short: α受体拮抗剂，禁与β受体拮抗剂合用。

    口诀：α拮抗扩血管，麦角林最典型。
  ```

- 分类口诀 → 写入该分类 `summary.short` 末尾，类似规则。

**反模式**：

1. ❌ 只有独立口诀节点，没在主知识节点的 `summary` 同步内嵌——用户看不到。
2. ❌ 只在主知识节点 `summary` 里写口诀，没建独立 `mnemonic` 节点——图谱里没有这条口诀的边。
3. ❌ 把药物口诀写到分类节点的 `summary` 里（口诀归属错位）。

### 5.13 表格节点（`table`）的父级规则

| 表格所在位置                  | 父节点                        |
| ----------------------- | -------------------------- |
| **章节级**对比表（多个分类下的药物横向比较） | **节节点**（如"第四节 抗记忆障碍及改善神经功能药"） |
| **分类内**对比表（同一分类下多个药物）    | 该**分类节点**（classification）   |
| **药物级**对比表（单药物内部项目对比）   | 该**药物节点**（medication）       |

**正模式**：

1. ✅ 表格单独建独立 `essence: table` 节点，**由表格节点自身**的 `edges_out` 写 `support →` 上表所列的父节点（节 / 分类 / 药物）。理由：新增对比表时只新增表 md，不必回去修改父节点（参见 §5.15）。
2. ✅ 表格节点的 `summary.full` 用 Markdown 表格语法（marked + DOMPurify 已放行 `table/thead/tbody/tr/th/td`）。

**反模式**：

1. ❌ 章节级对比表挂到分类节点（越级）。
2. ❌ 把 Markdown 表格直接塞进分类节点的 `summary.full`，不建独立 `table` 节点（违反 §3.4 阈值判断）。
3. ❌ 表格节点的 `summary.full` 是空字符串——表格内容必须写在 `full` 里。

### 5.14 同名节点文档的重写规则

> **两层规则区分**：
> - **frontmatter（YAML 块）**：严格遵守用户资料，不可擅作主张——见 §5.8（summary 填写）、§5.11（格式）。
> - **正文（`# …` 之后的 Markdown 正文）**：宽松处理——保留即可，不强制清空。
>
> 原因：frontmatter 是图谱的结构化元数据（字段决定节点在图谱中的位置、关系、检索结果），必须精确；正文是非结构化描述，用户通常不会逐字段提供，且对图谱结构无影响。

**触发条件**：发现已存在同名（或同 `id`）的 `.md` 节点文档，需要用新资料重写。

#### 5.14.1 frontmatter 字段（严格重写）

按以下表格处理 frontmatter 各字段，**与 §5.8 summary 字段填写原则同源**：

| 字段                       | 重写时怎么处理                                              |
| ------------------------ | ----------------------------------------------------- |
| `data.id`                | **沿用旧值**（保持 ID 不变以免破坏所有指向该节点的边）                     |
| `data.label`             | **沿用旧值**（除非用户明确要求改名）                                  |
| `data.location`          | **可参考**（仅作为目录位置依据，不强制沿用）                             |
| `data.essence`           | **不沿用**，按新资料重新判定                                     |
| `data.level`             | **不沿用**，按 §4 重新赋值                                    |
| `data.tags`              | **不沿用**，按 §5.11.4 重新抽取                                 |
| `data.edges_out`         | **不沿用**，按新资料重建（不保留旧边，除非用户明确指示）                       |
| `summary.short`          | **不沿用旧文本**，按用户新资料重写                                  |
| `summary.full`           | **不沿用旧文本**，按用户新资料重写（用户未提供的部分必须留空，不擅自补）                 |

**铁律**：

1. ❌ **不**因"沿用比重新写安全"就保留旧值——除非该字段不在本表"不沿用"列。
2. ❌ **不**因"旧文档里有合理内容"就复制粘贴到新文档——必须由用户提供为准。
3. ❌ **不**因"用户没说就按惯例补"——见 §5.8。
4. ✅ 用户资料缺失时（如只给药名没给临床信息），**主动列出哪些字段无资料、等待用户补充**，而不是擅自补默认值。

#### 5.14.2 正文（宽松保留）

| 场景                                              | 正文处理                                       |
| ----------------------------------------------- | ------------------------------------------ |
| 已有同名节点，**正文已有内容**，未要求重写正文                  | **保留旧正文**，不强制清空、不强制重新组织                 |
| 已有同名节点，**正文已有内容**，用户明确要求"重写正文"             | 按用户提供的新正文替换；用户未提供的段落保留旧版或留空（视用户原话判断）       |
| 已有同名节点，**正文已有内容**，AI 判断旧正文与新 frontmatter 矛盾 | **不动正文**（frontmatter 严格、正文宽松——矛盾由用户裁决）  |
| **新增节点**，用户**未提供正文**                          | **正文留空**——不写占位符、不写"待补充"、不写任何"AI 润色段" |
| **新增节点**，用户**提供了正文**                           | 原样写入，不二次润色（参见 §5.8 正模式 2）                |

**铁律**：

1. ❌ **不**因"旧正文存在就更顺手清空"——用户没要求就保留。
2. ❌ **不**因"frontmatter 重写了就显得正文过时"就清空正文——这是两套规则，不要混用。
3. ❌ **不**因为新增节点没正文就写一段"占位说明"或"AI 自动生成的简要描述"。
4. ✅ 新增节点无正文时，文件中可以**完全不包含**正文区（即 frontmatter 后直接 EOF；或 frontmatter 后只留一个空行）。

#### 5.14.3 汇报约定

重写同名节点时，在最终汇报里**分层汇报**：

- **frontmatter 部分**（按 §5.14.1 表格逐字段说明）：
  - "沿用"（id / label / location）
  - "用户提供"（short / full 哪几段）
  - "未提供，留空"（哪些字段用户没给）
  - "未提供，等待补充"（哪些字段用户没给且影响图谱完整性）
- **正文部分**（按 §5.14.2 表格说明）：
  - "保留旧正文" / "按用户新正文替换" / "正文留空（用户未提供）"

若 frontmatter 中用户未提供的字段**影响图谱结构性正确性**（如 `edges_out` 缺失导致节点无入边/无出边），**主动提醒**用户补充，而不是擅自建一条占位边。

#### 5.14.4 判断锚点（self-check）

| 问自己                              | 答案                                    |
| -------------------------------- | ------------------------------------- |
| 我要改的是 frontmatter 字段？          | 默认答案：**不能擅自动手**——必须等用户提供；缺失就留空并提醒       |
| 我要改的是正文？                       | 默认答案：**能不动就不动**——除非用户明确要求重写            |
| 我面对的是新增节点，用户没给正文？              | 默认答案：**正文留空**，不写任何内容                    |
| 如果我不在场，用户能否接受我写进文件的每一字（frontmatter）？ | 不能 → 留空、汇报、等待；能 → 写                  |

### 5.15 `edges_out` 字段填写原则

> 与 §5.8（summary）、§5.14（重写）一起，构成"frontmatter 三铁律"——但 `edges_out` 是其中**最宽松**的一节：边类型受限于 frontmatter 规定的 6 种，**具体 reason 措辞和挂边判断 AI 可发挥主观能动性**。
>
> 与 §5.8（summary 严格）和 §5.14（重写严格）形成对比——本节是"AI 可主动判断"区，但有 3 条铁律。

#### 5.15.1 边方向铁律：每个节点自管自己的 `edges_out`

**核心**：所有 `edges_out` 都表示**"这个节点向外辐射的引用关系"**。任何关系的发起方都在自己的 md 文件里写。

| 方向规则                       | 由谁写                                |
| -------------------------- | ---------------------------------- |
| **父子层级**（level 大→level 小）  | 子节点写 `parent → 父节点`                |
| **辅助学习**（口诀/注意/对比表 → 主知识）   | **辅助节点**写 `support → 主知识节点`        |
| **同级对比**（同 level 之间的横向对比）   | **任一侧**写 `contrast → 对侧`（双向视觉）   |
| **药学关系**（治疗/禁忌/相互作用/代谢）     | **业务主动方 / 提供方**写 `link → 目标节点`    |
| **一般关联**（弱参考）              | **任一侧**写 `relate → 目标`（推荐 level 较大的） |

**禁止**：

1. ❌ 父节点（level 小）写一堆 `edges_out` 指向子节点（level 大）——新增子节点时必须回来改父节点。
2. ❌ 子节点写 `parent → 父节点` 的同时又写 `support → 父节点`——同方向重复。
3. ❌ 双向边正反都写（同一对节点同时 A→B 和 B→A 两条 `parent` / `support` / `relate`）——单向即可。
4. ❌ 用 `parent` 来表达 `support`（"口诀属于药物的层级"是错的，口诀是辅助不是子分类）。
5. ❌ 把节点之间的引用全部塞到父节点里（错把"全局索引"当成 `edges_out`）——这是数据冗余和编辑耦合。

**正模式**：

1. ✅ **新增子节点时**：只需新建该子节点的 md 文件，写自己的 `parent → 父节点`。**不必回去修改父节点**。
2. ✅ **新增口诀节点时**：只需新建口诀 md，写 `support → 主知识节点`。**不必回去修改主知识节点**。
3. ✅ **新增对比表节点时**：只需新建表 md，写 `support → 父分类/节节点`。
4. ✅ **业务主动方写边**：药物 A 提到"与 B 相互作用" → 在 A 的 `edges_out` 写 `link → B`，不在 B 里写。
5. ✅ **同 level 的 contrast**：A 和 B 互为易混药时，A 写 `contrast → B`（单边即可，渲染端补双向视觉）。

#### 5.15.2 边类型选择决策表

| 关系                          | 用什么 type | 方向（写在谁的文件里）  | reason 措辞规范               |
| --------------------------- | -------- | ------------ | ----------------------- |
| 药物 A 属于分类 X                | `parent` | 药物 A 写       | `属于{分类名}`                |
| 药物 A 属于节节点 / 章节点           | `parent` | 药物 A 写       | `属于{节/章名}`               |
| 分类 X 属于节节点                 | `parent` | 分类 X 写       | `属于{节名}`                 |
| 节节点 属于章节点                 | `parent` | 节节点写         | `属于{章名}`                 |
| 药物 A 治疗疾病 B                | `link`   | 药物 A 写       | `治疗{疾病名}`                |
| 药物 A 引起不良反应 B              | `link`   | 药物 A 写       | `导致{ADR名}`                |
| 药物 A 禁用人群 B（孕妇 / 儿童 / 老人）   | `link`   | 药物 A 写       | `禁用{人群}`                 |
| 药物 A 配伍禁忌 B                | `link`   | 药物 A 写       | `配伍禁忌——{说明}`             |
| 药物 A 的机制是 B                | `link`   | 药物 A 写       | `机制——{说明}`               |
| 药物 A 被 B 代谢                | `link`   | 药物 A 写       | `被{B}代谢`                |
| 口诀节点 ↔ 药物/分类               | `support` | **口诀节点**写     | `{主知识名}记忆口诀`            |
| 注意/提示节点 ↔ 药物                | `support` | **注意节点**写     | `{药物名}注意事项`             |
| 对比表节点 ↔ 分类/节                | `support` | **对比表节点**写    | `{分类/节名}药物对比`           |
| 药物 A 易混于药物 B               | `contrast` | **任一侧**写     | `易混于{药名}`               |
| 任意两节点的弱关联                  | `relate`  | **任一侧**写     | 自由措辞，但不少于 4 字（如 `同类退热药参考`） |

#### 5.15.3 `reason` 措辞规范

- **必填**：所有 `edges_out` 条目都必须有 `reason`（参见 §2 关键迁移规则 2）。
- **AI 可发挥主观能动性**：reason 措辞不必逐字按用户原文，可基于上下文重新组织。
- **最低要求**：
  - 必须包含**具体对象**（药名 / 分类名 / 疾病名 / 机制名）——不能是"治疗""相关""适用"等空泛词。
  - 必须能独立成句——读者看到 reason 即可理解这条边的语义。
- **建议模板**（参考上表）：
  - `parent`：`属于{上级名}`
  - `link`：`{动词}{对象}`，如 `治疗癫痫`、`导致粒细胞缺乏`、`禁用孕妇`
  - `support`：`{主知识名}{角色}`，如 `倍他司汀记忆口诀`、`癫痫药物对比`
  - `contrast`：`易混于{药名}` 或 `对比{分类}内的代表药`
  - `relate`：自由措辞，不少于 4 字

**正模式**：

```yaml
edges_out:
  - target: class-amide
    type: parent
    reason: 属于酰胺类
  - target: med-piracetam
    type: support
    reason: 吡拉西坦记忆口诀
  - target: med-oxiracetam
    type: contrast
    reason: 易混于吡拉西坦（都是酰胺类促智药）
```

**反模式**：

```yaml
edges_out:
  # ❌ 父节点写一堆子节点——耦合、不可扩展
  - target: med-piracetam
    type: parent
    reason: 属于本分类
  - target: med-aniracetam
    type: parent
    reason: 属于本分类

# ❌ 辅助方反向——新增口诀时需改药物
# ❌ reason 空泛
  - target: med-piracetam
    type: support
    reason: 相关
```

#### 5.15.4 占位边禁止

- ❌ **不得**为"看起来完整"就建占位边（如 `link → adr-unknown` 占位未知 ADR）。
- ❌ **不得**为尚未确认的关系预先建边（如用户只说"可能与 X 相互作用"就建 `link → X`）——遇到不确定的，明确告知用户"该关系需要确认，是否建边"。
- ✅ **占位边**只能在 §5.14 重写场景下临时使用，且必须用 `placeholder: true` 标记 + 汇报里单独列出。

#### 5.15.5 汇报约定（edges_out 部分）

创建/重构一个节点时，汇报里**必须**列出 `edges_out` 每条边的来源：

| 来源                  | 汇报措辞                   |
| ------------------- | ---------------------- |
| 用户明确告知              | "用户提供：…→{target}（{reason}）" |
| AI 基于用户资料推断（边类型 / reason 措辞） | "AI 推断：…→{target}（{reason}）——基于用户提供的'{用户原话关键句}'" |
| 沿用旧值                | "沿用旧边：…→{target}（{reason}）" |
| 未提供 / 留空            | "未提供，留空：应挂 …→{target}（待用户确认）" |

#### 5.15.6 判断锚点（self-check）

| 问自己                                                | 答案                                              |
| -------------------------------------------------- | ----------------------------------------------- |
| 这条边写完后，**新增一个新子节点 / 辅助节点时**，是否需要回到这条边的发起方文件里改 `edges_out`？ | **不需要** → 写法正确；需要 → 方向反了或位置写错              |
| 这条边的 `edges_out` 写在**level 较小 / 业务提供方**那一侧的 md 文件里吗？ | 是 → 正确；否 → 改为业务主动方那一侧                          |
| 我要用 `parent` 还是 `support`？                        | `parent` = 层级归属（level 大→level 小）；`support` = 辅助学习 |
| reason 是否包含具体对象？                                   | 是 → 正确；否 → 补具体名词                                |
| reason 是否和用户原话差距过大？                                | 差距过大 → 汇报里告知用户"措辞偏离了原意"                     |

### 10.2 层级链

```
第一章 (module, L1)
  └─parent─ 第四节 (module, L2)
      ├─parent─ 酰胺类 (classification, L3)
      │           ├─parent─ 吡拉西坦 (medication, L4)
      │           ├─parent─ 茴拉西坦 (medication, L4)
      │           └─parent─ 奥拉西坦 (medication, L4)
      ├─parent─ 乙酰胆碱酯酶抑制剂 (classification, L3)
      │           ├─parent─ 多奈哌齐 (medication, L4)
      │           ├─parent─ 加兰他敏 (medication, L4)
      │           ├─parent─ 利斯的明 (medication, L4)
      │           ├─parent─ 石杉碱甲 (medication, L4)
      │           └─parent─ 酰胺类分类口诀 (mnemonic, L4) ─support→ 乙酰胆碱酯酶抑制剂
      └─parent─ 其他改善脑功能药 (classification, L3)
                  ├─parent─ 倍他司汀 (medication, L4) ←support─ 倍他司汀口诀 (mnemonic, L4)
                  ├─parent─ 丁苯酞 (medication, L4) ←support─ 丁苯酞口诀 (mnemonic, L4)

                  └─parent─ 长春西汀 (medication, L4)
```

> **ASCII 图的箭头方向**：子→父用 `├─parent─`（左侧起笔）；辅助→主用 `←support─`（箭头朝左、由辅助节点指向主知识）。
>
> 实际 md 文件里，`edges_out` 永远写在**发起方**那一侧：
> - `parent` 写在**子节点**（medication / classification / section / chapter / book）文件里。
> - `support` 写在**辅助节点**（mnemonic / note / table）文件里。
>
> 详见 §5.15。

### 10.3 边类型使用

整个样板仅使用 2 种边类型：

| 边类型       | 发起方（写在谁的文件里） | 数量               |
| --------- | -------------- | ---------------- |
| `parent`  | **子节点**（medication / classification / section） | 20 条（每个非根节点 1 条） |
| `support` | **辅助节点**（mnemonic 口诀） | 4 条（每个口诀 1 条 `support→` 主知识） |

不使用 `link`/`relate`/`branch`/`contrast` — 临床关系全部在 `summary.full` 文本中。

### 10.4 关键设计决策

1. **无冗余空模块**：不建"分类与代表药品"和"临床用药评价"空模块。层级链直接章→节→分类→药物。
2. **临床内容在 summary.full**：药理/适应症/禁忌/相互作用全部写入 summary.full 的【标签】格式文本。
3. **口诀与药物同级**：口诀 level=4，与药物同级（不是更深层级），因为口诀是药物的平行学习辅助，不是层级子分类。
4. **口诀的 `support` 边由口诀节点发起**（不是由药物节点发起）：口诀节点在自己的 md 文件里写 `edges_out: - target: med-betahistine, type: support`。理由：新增一个口诀时只需新增口诀 md，不必回去修改药物节点的 `edges_out`。这与 §5.15 的"自管 `edges_out`"原则一致。
