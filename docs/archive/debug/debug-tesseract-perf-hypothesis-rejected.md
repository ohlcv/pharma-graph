## 问题描述

加入「四维空间（tesseract）」装饰节点后，主观感觉：

1. **初始加载明显变慢**
2. **力布局（euler）运行期间帧数大幅降低**

怀疑该节点（真实 cytoscape 节点 + 独立全屏 canvas 逐帧重绘）在布局每帧都整幅重绘，把主线程占满。

## 环境

- 构建：`npm run build` + `vite preview`（**不用 dev server**，排除 HMR / 冷启动噪声）
- 数据规模：1182 节点
- 采样：Playwright，`1600×1000` 视口，页面加载后立即开始 rAF 打点，跑满 22s（覆盖 euler 全程）
- 指标：rAF 帧间隔分布（中位 / p90 / p99 / max）+ 长帧（>50ms）占比

## 排查过程

### 第一层：先确认「装饰节点开着时有多慢」

只测全开状态：

```
中位帧间隔 115.7ms (≈8.6 FPS)，p90 140.7ms，长帧占比 61.8%
```

结论：帧率确实很差 —— **但这只能说明「慢」，不能说明「是谁慢」**。1182 节点的 euler 本身就慢，这是没有对照组的裸数据。

### 第二层：单独关掉超立方体

在 `main.ts` 加开关，只关超立方体、保留太极八卦（两者机制完全相同，构成干净对照）：

| 指标 | 全开 | 只关超立方体 |
|---|---|---|
| 中位帧间隔 | 115.7ms | 128.2ms |
| 长帧占比 | 61.8% | 62.1% |
| 平均 FPS | 10.7 | 9.2 |

**关掉之后没有变快，反而略差。** 初步否证「超立方体是元凶」。

### 第三层：四组对照 + URL 开关

把两个装饰节点都做成 URL 可控（`?decor=off|celestial|tess`，缺省全开），在一台 server 上跑完所有组，避免反复构建带来的噪声：

| 组合 | 太极 | 超立方体 | 中位ms | FPS | 长帧% |
|---|---|---|---|---|---|
| `decor=off` | 关 | 关 | 116.4 | 8.6 | 79.9% |
| `decor=celestial` | 开 | 关 | **104.7** | **9.6** | 81.3% |
| `decor=tess` | 关 | 开 | 110.2 | 9.1 | 81.8% |
| 缺省（全开） | 开 | 开 | 120.2 | 8.3 | 80.4% |

## 结论

1. **四组差异全部落在测量噪声内**，长帧占比都死在 80% 上下。装饰节点对布局帧率**没有可观测影响**。
2. **全关（`off`）不是最快的一组**，最快的反而是只留太极八卦 —— 说明两套装饰之间也不存在互相挤占。
3. **「加载变慢」也没被证实**：`domReady` 在四组间是 1191ms / 2006ms / 4187ms / 13038ms，跨度 10 倍，但这个顺序与装饰节点数量**不相关**（只留一个的那两组反而一个最快一个最慢）。这是 preview server 冷启动 + 浏览器缓存状态的噪声，不是真实负载差异。
4. **真正的瓶颈在 euler 布局本身**，装饰节点只是恰好和它一起被引入，时间上相关但非因果。
   （euler 已内置 Barnes-Hut 四叉树，是 O(n log n) 而非 n²——所以瓶颈不是邻接规模，
   而是**每帧重复 30 次全图 pass** 这个高频。详见「遗留 / 下一步」。)

## 处理

- **不删除** `createTesseractOverlay()` 调用。保留 `?decor=` URL 开关（`src/ui/main.ts` 的 `DECOR_OVERRIDE`）作为后续对照实验工具，默认仍是两个都开。
- 早期版本曾在注释里写「实测它把帧率拖到 8.6 FPS」—— 那是**把裸数据当成了因果结论**，已更正为四组对照数据。

## 遗留 / 下一步

如果确实要提升布局期帧率，该优化的是 euler 本身，而不是装饰节点。

### ❌ 已排除：分层 / 分块布局

曾设想「先对子图布局，再整体展开，避开 1182² 的邻接计算」。**该方案不成立**，理由如下（2026-09-28 核查 `node_modules/cytoscape-euler/src/` 后得出）：

1. **euler 已内置 Barnes-Hut 四叉树**，斥力是 O(n log n) 近似而非 n² 暴力枚举：

   ```js
   // src/euler/quadtree/index.js —— s/r < θ 时把整个内部节点当作单体算力
   if ((node.right - node.left) / r < theta) { ... }
   ```

   参数链路完整、可调：`defaults.theta: 0.666` → `assign` 进 state → `tick()` 解构
   `theta` → `updateBodyForce(body, gravity, theta, pull)`。
   所以**不存在 1182² 的邻接瓶颈**——原设想的前提本身就是错的。

2. **即便如此，分块/分层仍无收益**。因为 euler 走的是逐帧连续动画路径
   （`animate: true` → `animateContinuously`），每 rAF 跑 `refresh`（默认 30）次 tick，
   且**每次 tick 都全量重建四叉树**：

   ```js
   // src/euler/tick.js
   quadtree.insertBodies( bodies );
   ```

   分块只在「整图一次性布局」时有意义。切成子图分别跑，块与块之间的跨块斥力/引力
   仍需一次全局计算才放得下——那正是 euler 现在每帧都在做的事，分块省不下来，
   反而多出子图合并的开销。

3. **分块没有自然的依据**。按章节切？按关系类型切？跨块边会丢失，
   合并回整体时需要重新处理这些边——最终仍是一次全图计算。

结论：分块/分层这条路在 cytoscape-euler 的实现下**没有收益，不建议尝试**。

### 真正的开销在哪

**已实测（下方对照表），此前基于静态代码的猜测全部被推翻。** 先纠正两个错误数字：

- **`refresh` 实际是 10，不是 30。** `config.ts` 的 `params[]` 里那个 slider 标着
  `default: 30`，但 `refresh` 从未写进同级的 `cytoscape` 配置块，只有用户手动拖过 slider
  存进 localStorage 时才经 `coerceStoredParams` 变成 override 生效。全新会话不走 override，
  用的是 `cytoscape-euler/src/layout/defaults.js` 的 `refresh: 10`。
  （该 slider 的 default 已于本次修正为 10，消除「面板显示 30 / 实际跑 10」的误导。）

### ❌ 已排除：布局质量降级

用 `?quality=` 开关跑全量对照（Playwright 无头 Chromium，1182 节点，每档 3 次取中位数）。
质量用两个几何指标衡量，不靠主观判断：**节点重叠率**（越低越好）与**边交叉数**（越低越好，
力布局质量的核心指标），均从收敛后最终位置计算。

| 变体 | 时长 | FPS | 中位帧 | 长帧% | 重叠% | **边交叉** | 铺开范围 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **baseline** | 20877ms | 7.5 | 133.4 | 90.8 | 0 | **138** | 17571×17265 |
| refresh5 | 20893ms | 7.5 | 133.4 | 88.9 | 0 | 409 | 12406×13770 |
| refresh2 | 20900ms | 8.6 | 116.7 | 87.0 | 0 | 2355 | 8211×9734 |
| theta (0.9) | 20899ms | 7.5 | 133.3 | 90.0 | 0 | 140 | 14277×17187 |
| time8s | 8935ms | 7.5 | 133.3 | 74.0 | 0 | 575 | 9971×11564 |
| frugal | 8769ms | 8.6 | 116.7 | 71.8 | 0 | 2558 | 7210×9482 |
| crippled | 3824ms | 15.0 | 66.6 | 51.2 | **31.1** | **140773** | 1878×1802 |
| preset（不跑 euler） | 0ms | 29.9 | 33.4 | 9.9 | **493.7** | **170944** | 754×723 |

**结论：降级换不来帧率，只换来了质量损失。**

1. **降 `refresh` 几乎不改善 FPS**（7.5 → 7.5 / 8.6），却把边交叉数从 138 推高到
   409 / 2355（3× / 17×）。曾假设「每帧 30 次全图 pass 导致帧率低」——数据否证：
   把每帧 tick 数砍到 1/5，帧率纹丝不动，而布局明显变差。
2. **真正能省时间的两档（time8s 砍半、crippled 快 5×）代价都是质量崩坏**。
   crippled 重叠率 31%、交叉数 140773，截图确认节点几乎全叠成一团，完全不可用。
3. **`theta` 0.666 → 0.9 几乎无变化**（138 → 140）。斥力近似精度对这个图不敏感，
   这条路可彻底划掉。
4. preset（完全不跑 euler）虽然 FPS 29.9 / 长帧仅 9.9%，但重叠率 493.7%、
   交叉数 170944 —— 它只是**质量地板**，不是可用方案。

**根本原因：帧率与布局质量在这个图上不解耦。** 二者由同一份计算开销决定，
降级省下的是「算够」的那部分，代价直接是「算对」。二者不可分离，
因此「用质量换帧率」在本图上不成立。

### 仍未尝试的方向

若还要继续优化，需找**不牺牲质量**的路径，目前均未验证：

- 换布局算法（如 dagre 分层，对有向图是 O(V+E) 且质量可预测）
- 把 euler 换成**同步一次性**（`animate: false`）——牺牲动画过程，但总计算量不变，
  帧率指标将失去意义（阻塞主线程），只在低频触发时有意义
- 加载期先渲染静态骨架、待布局稳定再挂装饰层
- 装饰节点的 canvas 在布局期间降频 —— 鉴于本文件首节结论，预期收益接近 0，优先级低
